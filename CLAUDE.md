# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Rules

- **Do NOT push to git automatically**: Never run `git push` after code edits unless the user explicitly requests a push. The user prefers to review changes locally and push manually.

## What this is

Pipe Assessor is a no-build static web app with two self-contained pages: `index.html` (~4000 lines: HTML + `<style>` + `<script>`) evaluates pipe wall-thickness integrity per **ASME B31.3** (required thickness / MAWP) and **ASME PCC-2** (repair category advice), with API 574 structural minimums as a secondary check — field engineers/inspectors enter measured wall loss and get a status (OK / MONITOR / REPAIR), remaining life estimate, and a generated PDF engineering report. `findings.html` is the **Findings Tracker** (see its own section below): a Supabase-backed register of abnormal inspection findings tracked from Open until repaired/closed. The calculator works standalone with no login; the tracker requires sign-in and a network connection.

No package.json or build tooling. Development consists of opening/editing `index.html` directly. CDN dependencies (pinned versions, loaded as static `defer` tags so the browser caches them for offline use):
- **Basecoat CSS 1.0.1** (`basecoat.cdn.min.css` + `basecoat.min.js`) — the user's preferred UI framework: shadcn/ui-style component classes (`.btn`, `.card`, `.input`, `.select`, `.field`) with brand colors mapped onto Basecoat's CSS variables (`--primary: #156B95`, etc.) in the first `<style>` block for both `:root` and `html.dark`.
- **jsPDF 2.5.2 + jspdf-autotable 3.8.4** — client-side PDF report generation. Do NOT bump versions without retesting (autotable 3.8.x pairs with jsPDF 2.x).
- **Leaflet 1.9.4** (`leaflet.css` + `leaflet.js`) — interactive **satellite** map for the Site Location feature (Esri World Imagery, `server.arcgisonline.com/ArcGIS/.../World_Imagery`; sends `Access-Control-Allow-Origin`, so tile canvases are exportable for the PDF). Satellite-only — no base-layer toggle. Opens at `DEFAULT_MAP_VIEW` (near the plant) so the user isn't panning across the country. **Online-only**: on offline `file://` the map is blank and the app degrades to coordinates-only (see the Site Location & Photos feature notes below).

## Deployment

- **GitHub**: `thanatKh/PipeAssessor`, branch `main`. Per the project rule above, changes stay local until the user commits and pushes themselves — nothing reaches the live site from an edit alone.
- **Hosting**: Render, serving the repo as a static site (no `render.yaml` in the repo — configured via the Render dashboard). Deploys automatically on push to `main`.
- **Real deployment target is `https://`, not `file://`.** The user's day-to-day usage is the live Render URL from a laptop and a phone — `file://` is a secondary/offline mode, not the primary one. This matters for a few things documented elsewhere in this file as `file://`-specific caveats:
  - The Leaflet/GPS "may fail on `file://`, not a secure context" caveat does **not** apply on the deployed `https://` site — `navigator.geolocation` should work normally there.
  - The native-PDF-viewer `blob:` URL approach (`openPdfNative`) was specifically validated to survive the `file://` edge case; it also works on `https://`, so no separate code path is needed there.
  - CDN dependencies (Basecoat, jsPDF, Leaflet, fonts) still load over the network on every real visit — a mobile connection dropping mid-load is a realistic scenario to consider, not just a `file://`-offline edge case.
- **Real mobile usage**: the phone is an actual device, not just a resized desktop browser — camera capture (`capture="environment"` on the photo input) opens the real camera app, GPS is real device location, and touch/viewport behavior should be verified against real mobile Safari/Chrome quirks, not only Playwright's mobile viewport emulation.

## Findings Tracker (`findings.html` + Supabase)

Phase 1 of turning the calculator into a piping-integrity management tool: a register of **abnormal findings** from vendor inspection reports, each tracked through a status lifecycle until repaired — the design goal is "no finding is ever forgotten." Deliberately finding-centric: there is **no pipe-asset register or CML/TML model** (the pipe tag is a plain field on the finding, with autocomplete from previously entered tags); don't add one without the user asking.

- **Architecture**: a second self-contained page (own `<style>`/`<script>`, no build step), sharing the design system with `index.html` by **duplication**: the Basecoat token-alias block, the `:root`/`html.dark, body.dark` palette variables, the header pattern, and the `theme` localStorage key (so light/dark follows across pages) are copied — keep the two files in sync when tuning tokens. The header logo uses the repo asset (`asset/RGB_OR_Full%20color.png`) directly instead of the base64 `OR_LOGO_DATAURL`, because this page is **online-only anyway** (Supabase + CDNs); offline it degrades to a login screen with a "check your connection" notice.
- **Backend**: Supabase project `uuwcftjduphtngmhwvrb` (**Singapore** region), URL + `sb_publishable_` key embedded as constants at the top of the page `<script>` — safe to commit; the anon key alone can read nothing because every table is RLS-gated to the `authenticated` role. CDN dep: `@supabase/supabase-js@2.49.4` UMD (pinned, `defer`, exposes `window.supabase`; the client instance is named `sb` to avoid clobbering that global).
- **`db/schema.sql`** is the single source of truth for the database — idempotent (safe to re-run), applied by pasting into the Supabase SQL Editor. Tables: `findings` (the core row: identity/source/anomaly/position/lifecycle groups), `finding_photos` (`kind` ∈ `found`|`repaired` — as-found evidence vs after-repair confirmation), `status_history` (the handover trail; the app inserts rows explicitly on every status change and on creation), and `assessments` (reserved for Phase 3 calculator snapshots — unused so far). **Status values are a check constraint AND a JS array (`STATUSES`)** — `'Open','Monitoring','Repair Planned','Repaired','Closed'` must match exactly in both places or updates start failing.
- **Auth model**: email/password only; public signups should be OFF in the dashboard and accounts created manually (Authentication → Users → Add user → Auto Confirm). All authenticated users have full read/write; audit is the `*_email` columns defaulted from `auth.jwt() ->> 'email'` at insert time (denormalized so the client never needs `auth.users` access). The `onAuthStateChange` handler deliberately re-routes **only when signed-in state flips** — routing on `TOKEN_REFRESHED` would re-render mid-edit and wipe unsaved form input.
- **Photos**: storage bucket `finding-photos` — public **read** (data non-confidential; paths are `findingId/uuid.jpg`, unguessable), authenticated write/delete. Every upload goes through the same mandatory `downscaleImage(…, 1600, 0.8)` as the calculator. Marking a finding **Repaired** with zero `repaired`-kind photos prompts a confirm (override allowed — the confirmation photo can arrive later).
- **Overdue logic** (`isOverdue`): `Open`/`Repair Planned` past `target_date`, or `Monitoring` past `next_check_date`. Powers the red KPI chip, list badges, and the detail banner — keep all three consistent.
- **Routing**: hash-based (`#/list`, `#/new`, `#/edit/<id>`, `#/f/<id>`) with a login gate; the map picker reuses the same Esri satellite source and `DEFAULT_MAP_VIEW` as the calculator.
- **Testing**: `verify-findings.js` (login gate, real wrong-credential round-trip to Supabase, theme, mobile) and `verify-findings-views.js` (stubs `findings`/`current` globals in-page to render list/detail/form without auth) in the session scratchpad — recreate from these descriptions if missing. Full CRUD testing needs a real account (create one in the dashboard); never commit credentials.

## Running / testing

- Open `index.html` directly in a browser (double-click or a static file server) — no build or install step.
- No automated test suite in the repo, but Playwright verification scripts are the established pattern: a scratchpad `baseline.js` (functional checklist: ERF overshoot pinning, validation paths, override switches, mode toggle, collapse+print force-open, reset confirm, theme persistence) and per-stage screenshot scripts (widths 1440/1024/820/390 × light/dark + print emulation), run via `node` with `APP_HTML` env var pointing at the file. Recreate these from the descriptions above if missing; verify in-browser rather than assuming correctness from code inspection.
- Note: headless Chromium does not paint iframe PDF viewers — verify generated PDF *content* by exporting the blob bytes and rendering pages with pdf.js (see the stage3-render.js pattern: base64 the blob out of the page, then render each page to canvas in a blank page with pdfjs-dist from CDN).

## Architecture

Everything lives in one file: `<head>` (CDN tags → Basecoat brand-variable override `<style>` → main app `<style>`) → HTML body (header with action buttons, mobile status strip + tab bar, two-column dashboard of `.card` sections) → single `<script>` block with all app logic. The generated PDF has no in-page dialog/iframe of its own — it opens in a new browser tab via the OS/browser's native PDF viewer (see `openPdfNative` below).

### Data flow

1. **Static data tables** (top of `<script>`): `PIPE_DATABASE` (NPS → OD + schedule→thickness, per ASME B36.10M) and `MATERIALS`. `getApi574Min(nps)` is the structural-minimum lookup.
2. **`initApp()`** (bottom of file) wires everything: theme restore (adds `.dark` to BOTH `body` and `documentElement` — Basecoat's dark component styles are gated on `html.dark`), renders `SCOPE_HTML` into `#scopeNotice`, calls `initSelections()`, `resetDefaults()`, `initHoverHighlighting()`, `initDragHandle()`, `initMobileTabs()`, `initLocationMap()`, `initLocationControls()`, `initPhotos()`, and attaches `input` listeners → `recalc()`.
3. **Every input change → `recalc()` → `runCalculations()`** (pure-ish, reads form fields, does the B31.3 math, returns `res`). `window.lastRes` caches the last result.
4. **`recalc()` pushes `res` into the DOM**: results table, `drawSvgPipe(res)`, `updateRepairAdvisor(res)`, `updateDynamicEquations(res)`, gauges, and the mobile status strip (`#mStatusVal`/`#mErfVal`).
5. No separate state store — the DOM is the state.

### PDF report subsystem (all client-side)

- `savePDF()` — async entry point: guards `hasErrors` and `window.jspdf` (falls back to `window.print()` if the CDN never loaded), then `buildPdfReport(res)` → `openPdfNative(blob)`.
- `buildPdfReport(res)` — A4 report (async): white header strip with the full-color OR logo (embedded base64 `OR_LOGO_DATAURL`, generated from `asset/RGB_OR_Full color.png` downscaled to 600px — regenerate the base64 if the asset changes), document info table, colored status band, inputs table, Figure 1 cross-section, results table with PASS/CHECK verdicts + FFS recommendation note when checks fail, substituted equations (real stacked fractions via `drawFractionRow`, computed from `res`, not scraped from DOM), PCC-2 bullets via `getAdvisorItems(res)`, **optional Site Location section** (coordinates + Figure 2 OSM map via `mapToPngDataUrl`, or a text fallback when offline), **optional Photographic Record section** (2-up `sitePhotos`, each framed with a `#cbd5e1` hairline border matching every table/figure border in the report), scope text from `SCOPE_TEXT`, signature block, then a centered "— End of Report —" closing marker so the last page has a deliberate stopping point instead of trailing into blank paper. **Only WinAnsi-safe characters** in PDF strings — jsPDF built-in fonts have no `≥`/`≤`/`·` middle-dot… actually `·` (U+00B7) *is* WinAnsi and is used in the equation fractions; the ones with no glyph are `≥`/`≤` (use `>=`/`<=`); em-dash/degree/bullet are fine. Section numbers are **auto-assigned by `sectionTitle` in draw order** (an internal `secNum` counter), so the two optional sections never leave a gap in the sequence when absent — never hardcode a `N.` prefix in a `sectionTitle` argument. Semantic status/verdict colors (status band fill, PASS/CHECK cell text, the CS-reference caveat, the FFS recommendation note) are **named constants `PDF_OK`/`PDF_WARN`/`PDF_WARN_DARK`/`PDF_WARN_MID`/`PDF_DANGER`** (declared next to `PDF_NAVY`, matching `:root`'s light-mode `--ok-color`/`--warn-color`/`--warn-text`/`--danger-color` exactly) — never re-type these as hex literals per call site, that's exactly how `--svg-metal`/`--primary-color` drifted from the design system before. The footer (drawn by `drawPageChrome()`, repeated every page) carries the same division/company attribution as the on-screen `.footer` block, so the report still identifies its issuing division once it's a standalone file.
- `svgToPngDataUrl(scale)` — serializes `#pipeSvg` to PNG for the PDF. Must inject a fixed light-palette `<style>` into the clone (CSS variables don't resolve in standalone SVGs; also keeps the diagram light in dark mode) and rewrite `<text>` font-family to Arial (Inter isn't available in the isolated SVG context). Strips the drag handle.
- `fetchLogoDataUrl()` — memoized, 3s timeout, resolves null on failure (expected on `file://`). Never draw a non-CORS `<img>` onto the SVG canvas — it taints it.
- `openPdfNative(blob)` — opens the PDF in a new tab using the **browser's own native PDF viewer**: no custom dialog, no iframe. Implementation is deliberately narrow: `URL.createObjectURL(blob)` on a real `<a href=... target="_blank" rel="noopener">` element, then `.click()`. Two other approaches were tried and both fail on `file://` (this app's primary no-build deployment mode) — do not reintroduce them: (1) `window.open('', '_blank')` followed by setting `.location` on the resulting blank tab hits `net::ERR_ABORTED`, because that blank tab can end up with a different opaque origin than its opener, and a `blob:` URL only resolves within the origin that created it; (2) a `data:` URL sidesteps that origin issue but Chromium blocks top-level navigation to `data:` URLs outright (anti-phishing, ~Chrome 88+) — the tab lands on `about:blank#blocked` instead. A `blob:` URL opened via a direct anchor click from the same document that created it is the one combination that actually works. There is no Save/Print/Share UI of our own anymore — the native viewer supplies its own.
- The old `window.print()` path (`@media print` stylesheet + `beforeprint`/`afterprint` collapsible-card force-open) is kept fully functional for Ctrl+P.

### Mobile layout (<768px)

Bottom tab bar (`#mTabBar`) switches `body[data-mtab]` between `inputs`/`results`; the two `.dashboard` columns (`#colInputs`/`#colResults`) are the panes. Sticky status strip (`#mStatusStrip`) above the tab bar mirrors the banner (updated in both `recalc()` branches). There is no Calculate button — every input change recalculates live via `recalc()`; on mobile the user switches to the Results tab manually. All rules scoped to `@media (max-width: 767px)`; print forces both columns visible.

### Site Location & Photographic Record (input cards → optional PDF sections)

Two optional data-capture cards live at the bottom of the inputs column (`#locCard`, `#photoCard`), so they flow into the mobile Inputs tab. Neither affects `runCalculations()` — they only add PDF sections.

- **Site Location** — lat/lng number fields (`#locLat`/`#locLng`) + a "Use my GPS" button (`navigator.geolocation`; may fail on `file://`, which Chrome doesn't treat as a secure context — manual entry is the reliable path) + an interactive **satellite-only** Leaflet map (`#locMap`) that opens at `DEFAULT_MAP_VIEW` (`{ center: [13.097720, 100.887211], zoom: 14 }` — change this constant to re-home the default view). `initLocationMap()` guards `typeof L` and, if Leaflet didn't load (offline first run), writes a text fallback into the container. Map click ↔ coordinate fields stay in sync via `setSiteLocation()`. State is the module-scope `locMap`/`locMarker` + the DOM fields (no separate store). The single satellite base layer is defined in `TILE_SOURCES.satellite` (used by BOTH the Leaflet layer and the PDF composer) with `activeTileSource` a constant `'satellite'` — mind the Esri axis order `{z}/{y}/{x}` (not OSM's `{z}/{x}/{y}`) in `tileUrl`.
- **Photographic Record** — `#photoInput` (`accept="image/*" capture="environment"` so mobile opens the camera) + a document `paste` handler. Every image goes through `downscaleImage()` (≤1600px, JPEG q0.8) before being pushed to the module-scope `sitePhotos` array — **downscale is mandatory** to keep the PDF/localStorage small (raw phone photos are 3–12 MP). Photos are held **in memory only** (lost on reload; not persisted to localStorage to avoid quota blowups). `resetDefaults()` clears both `sitePhotos` and the location marker/fields.
- **`mapToPngDataUrl(lat, lng, zoom, W, H, sourceKey)`** — composes the PDF's Figure 2 satellite top-view by fetching a clean tile grid via `TILE_SOURCES[sourceKey].tileUrl` (`crossOrigin='anonymous'`, so the canvas is untainted and exportable — Esri sends `Access-Control-Allow-Origin`), drawing a centre pin + the source's required attribution, and returning a PNG dataURL. This deterministic tile-composition avoids a fragile Leaflet DOM screenshot. It has a 7s timeout race and **resolves `null` on any failure** (offline/blocked), so `buildPdfReport` falls back to coordinates-as-text and never hangs or throws. Web-Mercator math: `fx = (lng+180)/360·2^z`, `fy = (1 − ln(tan φ + sec φ)/π)/2·2^z`.
- Print (Ctrl+P): `#locMap`, `.loc-gps-btn`, `.photo-add-btn`, `.photo-remove` are hidden via the `@media print` list (the interactive map would print broken); coordinate fields and photo thumbnails still print.

### Other key functions

- `runCalculations()` — core ASME B31.3 math; central place for calculation changes.
- `drawSvgPipe(res)` — SVG cross-section: a longitudinal wall-thickness *profile* (pipe wall unrolled into a straight strip, OD at top / nominal ID at bottom, in the `WALL_PLOT` constant's fixed pixel geometry), not a circular cutaway — the wall-loss pocket is a flat-bottomed dip with smooth shoulders (not a sharp V) drawn against horizontal limit lines (`t_req`, `t_req+CA`, `t_struct`), so a reader sees the dip visually cross a limit line when a check fails. viewBox is `0 0 500 270` — the extra width past the plot (`WALL_PLOT.right = 260`) is the leader-line label column; keep label text short enough to fit (labels are clipped in the PDF export path, which rasterizes the SVG at its exact viewBox size — unlike the live page, there's no forgiving extra width there). There is no side "wall gauge" panel — `#pipeSvg` has CSS `height: auto` so it scales by width alone at the true `500:270` ratio, filling `.svg-container` (`max-width: 900px`) rather than rendering at a fixed 500×270 and letterboxing.
- `getAdvisorItems(res)` — pure PCC-2 advisor content, shared by `updateRepairAdvisor()` (DOM) and the PDF.
- `updateDynamicEquations(res)` — on-screen equation blocks with substituted values.
- `initDragHandle()` — drag handle on the SVG adjusts wall-loss depth (vertical drag only, mapped through `WALL_PLOT`).
- `initHoverHighlighting()` / `HOVER_MAP` — cross-highlights SVG boundary/limit lines and their leader labels.

### Conventions to preserve

- Pressure entered in `bar`/`psi`, always converted to **MPa** internally (`pUnit` conversion in `runCalculations()`).
- Theme toggle sets `.dark` on **both** `body` (app CSS) and `html` (Basecoat), persisted to `localStorage`.
- Top app header (`body > header`, scoped so it doesn't hit `<header class="card-header">` cards) is a **theme-following surface** — light (`--header-bg: #fff`) in light mode, dark slate (`#0f172a`) in dark mode, with a thin `.header-accent-bar` (teal→sky gradient) on top and a `--header-border` bottom rule. The OR brand mark is the full-color logo (`OR_LOGO_DATAURL`, embedded — set into `#hdrLogo` in `initApp`, offline-safe) inside a **white `.hdr-logo-chip`** so it reads on both light and dark surfaces without a theme-swap (the logo's navy "OR" would vanish on a dark background bare). The header controls use the normal theme-aware `.theme-btn`/ghost-button styling — do **not** reintroduce fixed light-on-dark overrides (those were needed only by the old navy bar).
- Two input modes (wall-loss depth vs measured minimum) tracked via `.active` on `#modeSeg` buttons; mutually derivable (`t_meas = t_nom - depth`).
- Validation uses `aria-invalid="true"` attributes (Basecoat convention) + `.validation-alert` visibility; styled by a custom override rule, not Basecoat defaults alone.
- All numeric display formatting goes through `fmt(val, decimals)` (`—` for null/non-finite).
- Dense-engineering styling: JetBrains Mono + `tabular-nums` for all numeric values (`.res-val`, number inputs, equations), hairline borders, 12px spacing scale, `--radius: 0.5rem`. **Basecoat's `.card` ships its own 24px padding + gap** — the app zeroes those (`.card { padding: 0; gap: 0 }`) because spacing is managed via `.card-header`/`.card-body`; check for similar Basecoat spacing stacking when adopting new Basecoat components.
- Border-radius scale: **6px** for interactive controls (buttons, inputs, selects, dropdown-style elements), **8px** for containers (cards, the logo chip). Fully-rounded pill shapes (the toggle switch, the ERF gauge track) correctly use `radius = height / 2` regardless of this scale — that's required geometry, not drift. Tiny elements (the 10px legend swatch, the 4px gauge pointer) use a proportionally small radius for the same reason. When adding a new rounded element, pick 6 or 8 unless it's a pill or near-icon-sized, in which case scale the radius to the element's own size instead of forcing it onto the two-tier scale.
- Readability floor: 11px for anything meant to be actively read — field `label`s, `.hint`, `.validation-alert`, `.scope-notice`, equation legends, SVG cross-section labels. 10px is reserved for short uppercase badge/eyebrow-style text (`.res-section-title`, `.eq-status-badge`, `#mStatusStrip .m-strip-label`), where the bold weight + letter-spacing compensate. `.eq-box` (the static, non-substituted formula display) is `justify-content: flex-start` — don't recenter it; the internal `.fraction`'s own `text-align: center` is a different, necessary thing (centers the numerator/denominator over the fraction bar) and must stay.
- `.validation-alert` and `.hint` both carry real margin (6px) so an input's error message doesn't crowd the hint beneath it when both are visible at once; `.validation-alert + .hint` collapses the hint's own margin-top so the two don't double up.
- Transitions: the universal `* { transition: background-color, border-color, color, box-shadow, all 0.2s }` rule is the single source for state-change fades (focus rings, invalid-state rings, hover, theme toggle, the mobile tab bar's active-indicator box-shadow, etc.) — components should only declare their own `transition` for properties that rule doesn't cover (`transform`, SVG `r`/`stroke`/`fill`/`opacity`, `width`/`left` for gauge fills). When a state class changes a property, double-check it's actually in the relevant transition list — `.drag-handle.dragging` changing `stroke` without `stroke` in `.drag-handle`'s transition list was exactly this bug (fixed).
- Code-compliance box (`.compliance-box`, ids `compB313`/`comp574`/`ffsNote`): PASS/FAIL per ASME B31.3 (margin ≥ 0) and API RP 574 (t_meas ≥ t_struct), updated in both `recalc()` branches; when either fails, an API 579-1/B31G FFS recommendation note is shown (and mirrored in the PDF results section).
- Semantic status colors (`--ok-color`/`--warn-color`/`--danger-color`) and cross-section limit colors (`--limit-reqca`/`--limit-req`/`--limit-struct`) are CSS variables in `:root`/`body.dark`, each tuned per-theme — never hardcode their hex values in CSS or SVG attributes (the pressure gauge zones and cross-section limit lines/labels once did, which silently pinned them to one theme's shade regardless of which theme was active; a stray `[data-theme="dark"]` selector on the ERF gauge pointer/tip was dead CSS for the same reason, since theme is toggled via `.dark` on `body`/`html`, not a `data-theme` attribute — the pointer stayed black in dark mode until fixed to `var(--text-color)`). The `--limit-*` values are deliberately dark/saturated 700–800-tier shades (not the brighter 500-tier line colors elsewhere) so 11px bold SVG label text clears WCAG AA (4.5:1) against the near-white `--svg-bg` — this matters most for the PDF/print export, which always uses the light-theme values via the injected style block in `svgToPngDataUrl` (keep that block's hardcoded hex list in sync if `--limit-*`/`--svg-*` light values ever change).
- `SCOPE_HTML`/`SCOPE_TEXT` is the single source for the Scope & Limitations text (DOM notice + PDF section) — edit it in one place only.
