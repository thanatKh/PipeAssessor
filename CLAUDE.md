## Project Rules

- **Do NOT push to git automatically**: Never run `git push` after code edits unless the user explicitly requests a push. The user prefers to review changes locally and push manually.

## What this is

Pipe Assessor is a **Vite + Vanilla TypeScript** (no framework) single-page app: the Findings Tracker dashboard — a Supabase-backed register of abnormal piping inspection findings tracked from Open until repaired/closed, with a full **ASME B31.3** wall-thickness assessment workbench built in. The workbench evaluates required thickness / MAWP per ASME B31.3, checks API 574 structural minimums, and — via the standalone **Repair Advisor** — gives repair guidance per ASME PCC-2 (or the applicable standard for non-wall-loss damage). A field engineer enters the measured wall loss and gets a live status (OK / MONITOR / REPAIR), cross-section diagram, results table, repair advisor, substituted equations, remaining-life estimate, and a generated PDF engineering report. The whole app requires sign-in and a network connection (Supabase); offline it degrades to a login screen with a "check your connection" notice.

**History note:** this was originally a no-build single-file monolith (`index.html` + three classic-script `asset/*` files), then a standalone calculator (`calculator.html`) merged into the dashboard. Both migrations are complete and merged to `main`. Git history retains both prior forms if archaeology is ever needed; nothing below describes them further.

## Module map (`src/`)

- **`engine/`** — the ASME B31.3 engine, **strictly typed** (no `@ts-nocheck`): `compute.ts` (`computeB313` + re-exports), `pipe-data.ts` (`PA_PIPE_DATABASE`/`PA_MATERIALS`, extracted verbatim from the pre-migration `shared.js`), `format.ts` (`paFmt*`), `fonts.ts` (base64 Google Sans + `registerGoogleSansWebFont` for the web; `registerGoogleSansFonts` — async, loads Sarabun — for the PDF; see Thai text below), `branding.ts` (`OR_LOGO_DATAURL` + `downscaleImage`).
- **`legacy/shared.js`** — **frozen, not live code.** The pre-migration classic-script file, kept only as the baseline `compute.test.ts` diffs against (evaluated in a VM sandbox; `computeB313` must be bit-identical across a large size/schedule/material/mode/override matrix — must stay 0 mismatches). Never edit it and never import it from app code — to change the engine, change `engine/compute.ts` and update the parity test's expected divergences instead.
- **`workbench/`** — the ASME B31.3 result-display layer and the repair-advisor content, both strictly typed:
  - `assess-view.ts` — `paCreateAssessView(root, opts) → view`: injects the workbench markup into `root`, returns `{ render(res, ctx), getSvg(), getLastRes() }`. `opts.sections` picks blocks in order from `status | scope | svg | results | equations` (no `advisor` entry any more — see below); `opts.collapsed` lists sections rendered as closed `<details>`; `opts.onDepthDrag(depth_mm)` enables the SVG drag handle (omit for read-only views). `render(res, ctx)` takes a `computeB313` result (or `null`) and `ctx = { neutral, nps }` — `neutral: true` shows the grey "enter data to begin" banner instead of a red ERROR. Markup carries no element ids — every lookup is `data-k` scoped to the instance root, so multiple instances coexist in one document (form, detail page, quick calc). Also exports `PA_SCOPE_HTML`/`PA_SCOPE_TEXT` (Scope & Limitations text) and `paSvgToPng`/`paCrossSectionPng` (SVG→PNG rasterization for the PDF figure — injected fixed light-palette `<style>` must stay in sync with `theme.css`'s `--svg-*`/`--limit-*` values; never put `*/` inside a JS block comment in this area, it terminates the comment).
  - `repair-advisor.ts` — the **standalone Repair Advisor**, independent of (not nested inside) the B31.3 assessment panel, so it's always available regardless of finding type. `REPAIR_ADVISOR_BY_FINDING` is a per-finding-type content table (Coating, Pipe Support Defect, Dent, Other — each entry flagged `needsReview: true` since the guidance is a best-effort draft, not verified domain expertise). `resolveAdvisor(findingType, res, isLeaking?) → ResolvedAdvisor | null` is the precedence resolver: wall-loss types (`WALL_LOSS_TYPES`) with a valid non-error `res` get precise numeric advice (`paAdvisorItems(res, findingType)`) that is both **status-aware** (OK / MONITOR / REPAIR) and **mechanism-aware** — `corrMechOf(findingType)` + the `CORR_MITIGATION` table give External / Internal / CUI / CUS corrosion each their own remediation (external removal+recoat+CP vs. internal process-side control vs. CUI insulation/weatherproofing restoration vs. CUS support-detail fix); at OK it still calls out arresting the live corrosion (removal → recoat), and at REPAIR it **always** offers Replacement / Spool Replacement (not only above 80% loss). The numeric base carries `NUMERIC_STANDARDS_NOTE` + `needsReview: true`. Wall-loss types without a valid `res` get a generic "record a reading" prompt; non-wall-loss types always use their own table entry regardless of any stray `res`. `LEAKING_OVERLAY` is a separate safety-first content block (Immediate Safety / Root Cause / Interim Containment / Spool Replacement) **prepended** to whatever the base entry resolves to when `isLeaking` is true — Leak is **not** a finding type (see `core/constants.ts` below), it's an orthogonal flag any finding can carry. `paRenderRepairAdvisor(root, findingType, res, isLeaking?)` renders into a plain container — one panel, mounted independently in the form (`#raBody`), the detail page (`#raDetailBody`), and threaded into the PDF's "Repair Advisor" section (always renders, not gated on an assessment existing). **Advisor prose (summaries/body text) is in Thai**, but the panel title stays **"Repair Advisor"** in English, and **technical nouns inside the Thai text stay in English** too — material/method/equipment/standard terms like Composite, Epoxy, Mechanical Clamp, Pre-heat, NDT, WPS/PQR, Coating, Gouge, Sleeve, Support, Shoe, Hanger Rod are left untranslated (transliterating them into Thai script reads worse to a Thai engineer than the English term itself). Code comments and identifiers stay English throughout. Keep this split when editing — narrative sentences in Thai, technical terms in English, panel chrome/title in English.
- **`types/models.ts`** — `B313Inputs`/`B313Result` (strict) + persistence row types (loose, index-signatured, e.g. `Finding.is_leaking: boolean | null`).

**Extraction pattern**, if splitting a feature module further: (1) identify a block's true dependencies with an identifier scan against `core/`/other features; (2) extract with a small Node script (never hand-copy — base64 font/logo blobs break line-based tools, and hand-editing thousands of lines invites transcription bugs); (3) **validate with the TypeScript name-resolution guard** — temporarily strip the touched files' `@ts-nocheck` banners and set `strictNullChecks:false` in `tsconfig.json`, run `tsc --noEmit`, and grep for `TS2304` (missing name) / `TS2305`/`TS2307` (missing export/module) / `TS2540`/`TS2539` (illegal reassignment of a read-only import — the live-binding-state trap) / `TS2300`/`TS2451`/`TS2440`/`TS2448`/`TS2454` (redeclaration) / **`TS2552`** (a *near-miss* unresolved name — "Cannot find name X, did you mean Y?" — easy to miss if only grepping TS2304; caught a real bug where `pdf.ts` imported `paFmtDateTime` but the ported body called `fmtDateTime`, the `core/dom.ts` alias); restore the banners after. Run this after every extraction, not just at the end. (4) `npm run test` (parity) + `npm run build` (also confirms lazy chunks stay lazy) + a Playwright smoke test against the dev server or `npm run preview`. (5) **For anything touching saved data or PDF output, a generic smoke test is not enough** — a structurally-clean build can still have runtime bugs invisible to typecheck/build (e.g. a jsPDF text-measurement function like `splitTextToSize` silently mis-measuring Thai glyphs because it ran under the wrong active font at call time — not caught until an authenticated E2E test rendered a real PDF from real saved data and the text was visibly missing). Run an authenticated E2E pass (sign in with real test credentials, create → save → view detail → export PDF → delete a clearly-tagged test finding) before considering a change fully verified.

**Circular imports are sometimes correct here**: e.g. `form.ts` imports `show` from `../app` (the router's view-switcher genuinely lives in the hub) while `app.ts` imports form functions back — safe specifically because both sides are `function` declarations (hoisted), never `const` arrow functions, so the cycle resolves at call time, not at module-eval time.

**Thai text**: the web app and the PDF report use **different fonts for different reasons**, so don't assume changing one changes the other. Web: Google Sans has no Thai glyphs, so `'Noto Sans Thai'` sits right after `'Google Sans'` in the `html, body` font stack (`theme.css`), imported via `@fontsource/noto-sans-thai` at weights 400/500/600/700 in `main.ts`; its `@font-face` rules are `unicode-range`-scoped to the Thai block (`U+0E01-0E5B`) so it never touches Latin/numeric rendering — the browser's normal per-character font fallback does the rest. PDF: the report uses **Sarabun** (`https://fonts.google.com/specimen/Sarabun`, OFL-1.1) instead of Google Sans — chosen specifically because it natively covers **both** Latin and Thai glyphs in one face, so unlike the web split above there's no font-switching needed: `registerGoogleSansFonts(doc)` (`src/engine/fonts.ts`, now **async**) fetches `src/assets/fonts/Sarabun-{Regular,Bold,Italic,BoldItalic}.ttf` (sourced from the google/fonts OFL repo) as lazy Vite `?url` assets and registers all four faces under the jsPDF font name `'GoogleSans'` — deliberately kept as that name (not renamed to `'Sarabun'`) so the ~90 existing `doc.setFont('GoogleSans', …)` call sites across both PDF builders don't need to change. There is no more Thai-detection monkey-patch (`registerThaiPdfFont` is gone) — every `doc.text()`/`doc.splitTextToSize()` call renders correctly regardless of script, since it's one font for the whole document.

## Findings Tracker / Dashboard (`index.html` + Supabase)

The app's landing page and primary daily tool: a register of **abnormal findings** from vendor inspection reports, each tracked through a status lifecycle until repaired — the design goal is "no finding is ever forgotten." Deliberately finding-centric: there is **no pipe-asset register or CML/TML model** (the pipe tag is a plain field on the finding, with autocomplete from previously entered tags plus the master line list below); don't add one without the user asking.

**Location-first identity**: the app serves operators (who know *where* a problem is, not the Line No.) as well as engineers. So **Location Description is the required identity field and Pipe Tag / Line No. is optional** (`pipe_tag` is nullable — an engineer assigns the Line No. later). Everywhere a finding is labeled by its tag — register row, map popup, detail `<h2>`, both PDFs' tag column/header — it **falls back to `location_desc` when `pipe_tag` is empty** (`f.pipe_tag || f.location_desc || '—'`). (The findings **bulk import** still requires Pipe Tag — an engineer batch path, intentionally not changed.)

- **Backend**: Supabase project `uuwcftjduphtngmhwvrb` (**Singapore** region), URL + `sb_publishable_` key in `src/core/supabase.ts` — safe to commit; every table is RLS-gated to the `authenticated` role, **except the one public RPC described below**.
- **`db/schema.sql`** is the single source of truth for the database — idempotent, applied by pasting into the Supabase SQL Editor. Tables: `findings`, `finding_photos` (`kind` ∈ `found`|`repaired`), `status_history` (the handover trail), `assessments` (workbench snapshots: `{ inputs, results }`), and `line_list` (the master pipe-tag reference — see below). **Status values are a check constraint AND a JS array (`STATUSES`)** — `'Open','Monitoring','Repair Planned','Repaired','Closed'` must match exactly in both places. `findings.estimated_cost numeric` (nullable) holds the manual repair-cost estimate; `findings.is_leaking boolean not null default false` is the "Actively Leaking" flag (see below). **Adding a column to an existing DB requires an explicit `alter table … add column if not exists`** (see the patches near the top) — ship the migration before the code that writes the column, or every save fails with PostgREST 42703. `line_list` is created *before* section 6's RLS block (not appended at the very end) since that block enables RLS on it — keep that ordering if the file is restructured. **Section 8** is the public-share RPC (`get_public_finding`, see below) — also mirrored standalone in `db/public-share-migration.sql` for a one-off paste if section 8 alone hasn't been applied yet.
- **Auth model**: email/password only; public signups OFF, accounts created manually (Auto Confirm). All authenticated users have full read/write; audit is the `*_email` columns defaulted from `auth.jwt() ->> 'email'`. The `onAuthStateChange` handler re-routes **only when signed-in state flips** — routing on `TOKEN_REFRESHED` would re-render mid-edit and wipe unsaved form input.
- **Public read-only share links (QR code on the PDF report)**: the finding PDF's title block prints a small QR code (top-right, under the health banner) encoding `${PUBLIC_BASE_URL}/#/s/<finding-id>` — scannable from a printed report or tappable in a PDF viewer (`doc.link(...)` lays a click-through annotation over it), landing on a **read-only web view of that one finding with no sign-in required**. This is the app's only public (non-`authenticated`) read path, deliberately narrow:
  - **`public.get_public_finding(p_id uuid)`** (`db/schema.sql` §8 / `db/public-share-migration.sql`) is a `security definer` SQL function — it runs as the table owner (bypassing RLS) but returns **exactly one finding by id** as a single `jsonb` blob (`finding` with `created_by_email` stripped, plus its `assessments`/`photos`/`history`, other `*_email` columns also stripped). `anon` is granted `EXECUTE` on the function only, **not** `SELECT` on any table — so a visitor can fetch the one finding whose UUID they were given (via the QR/link), but cannot browse, list, or enumerate the register. No Cloudflare Worker involved and no service-role secret anywhere in the client — the whole mechanism is one Postgres function call through the existing anon-safe `sb` client. Revoke every outstanding link at once with `revoke execute on function public.get_public_finding(uuid) from anon;`.
  - **`loadPublicFinding(id)`** (`features/dashboard.ts`) calls the RPC via `sb.rpc('get_public_finding', { p_id: id })` and populates the exact same `current`/`currentPhotos`/`currentHistory`/`currentAssessments` state the authenticated detail page uses — so `renderDetail()` needs no public-specific branch; it just renders what's loaded.
  - **Routing**: `#/s/<id>` (`app.ts`'s `routePublic`) is intercepted **before** the `if (!session)` login gate, adds `body.public-view`, and calls `loadPublicFinding` — success renders the normal detail view, failure (bad/unshared id, RPC error) shows `#viewShareError`. `initApp` also stamps `public-view` on the body synchronously if the incoming hash is `#/s/…`, so a not-yet-authed visitor never flashes the login screen first.
  - **Read-only chrome**: `body.public-view` (CSS in `app.css`) hides every data-mutating/nav control — Edit details, status-change actions, photo Add buttons, Sign out, Line Risk, Quick Calc — and shows a "Read-only shared view — no sign-in required" badge (`.public-badge`) in the header. Export PDF stays available. Photos already load from R2's public bucket, so no extra photo-auth plumbing was needed.
  - **`PUBLIC_BASE_URL`** (`core/constants.ts`) is the deployed origin (`https://pipeassessor.onrender.com`) used to build the share URL baked into every PDF — update it if the Render URL/custom domain ever changes.
  - The `qrcode` npm dep is `await import()`-ed only inside `buildFindingPdf` (same lazy-chunk pattern as jspdf/xlsx) — it never touches the eager entry bundle.
  - The QR has **no caption text under it** ("Scan to view online" was tried and removed at the user's request, to keep the gap tight between the title block and the next section) — it's vertically centered against the two-row identity grid instead (`qy = y + (tbRowH * 2 - qs) / 2`). Identity-grid cell text sizes were also bumped up a notch (`tbCell`'s `fs` per call) for at-a-glance readability now that the caption isn't competing for space.
- **Photos**: stored on **Cloudflare R2** (bucket `finding-photos`), not Supabase Storage — moved there because Supabase's free-tier Storage cap (1GB) forced aggressive downscaling; R2's free tier is 10GB with zero egress fees. `finding_photos.storage_path` still just means "the object key," now resolved against R2 instead. **Reads** are a plain public URL (`photoUrl()` in `dashboard.ts`, `R2_PUBLIC_BASE` constant, R2's public `r2.dev` bucket access — same public-bucket model Supabase Storage used). **Writes/deletes go through a small Cloudflare Worker** (`worker/`, a separate project deployed independently via `npx wrangler deploy` — **not** part of the Vite build or Render's auto-deploy) because R2's write access can't be done safely from the browser the way Supabase's RLS-gated client can. The Worker (`worker/src/index.ts`) needs no secrets of its own: it uses a **native R2 binding** (`env.PHOTO_BUCKET`, no S3 access keys involved) and verifies the caller is logged in by calling Supabase's own `/auth/v1/user` endpoint with the browser's access token, using the same publishable key already committed in `src/core/supabase.ts`. `uploadPhoto`/`deletePhotos` (`form.ts`) call the Worker's `/upload`/`/delete` routes with `Authorization: Bearer <sb.auth.getSession() token>`. Every upload goes through `downscaleImage(…, 1600, 0.75)` inside `uploadPhoto` (bumped up from the old 900/0.55 once R2 removed the storage-budget pressure). **Capped at `PHOTO_LIMIT_PER_KIND` (4) per kind, 8 per finding** — enforced in `addDetailPhotos`/`addPendingFiles` and reflected in every "+ Add" button's `(n/4)` label/disabled state. Marking Repaired with zero `repaired`-kind photos prompts a confirm; the status-change dialog's Repaired step also has its own inline "After Repair photos" uploader. The old Supabase Storage bucket + its `storage.objects` RLS policies in `db/schema.sql` are now dead/unused config, left in place rather than migrated out.
- **Overdue logic** (`isOverdue`): `Open`/`Repair Planned` past `target_date`, or `Monitoring` past `next_check_date`. Powers the red KPI chip, list badges, the detail banner, and the map's Overdue legend swatch — keep all four consistent.
- **Routing**: hash-based (`#/list`, `#/new`, `#/edit/<id>`, `#/f/<id>`, `#/calc`, `#/risk`) with a login gate — **except `#/s/<id>`**, the public read-only share route, intercepted before the gate (see the public share bullet above).
- **Finding Type vs. Leak**: `FINDING_TYPES` (`core/constants.ts`) is 8 entries — External Corrosion, Internal Corrosion, CUI, CUS, Coating / Painting Damage, Pipe Support Defect, Dent / Mechanical Damage, Other. **`Leak` is deliberately not in this list** — a leak is a state orthogonal to damage mechanism (an External Corrosion finding, a Dent, etc. can each independently be leaking or not), modeled instead as the `is_leaking` boolean + an "Actively Leaking" checkbox (`#fIsLeaking`) in the form's Anomaly panel. Checking it auto-bumps Severity to High (same one-way `severityTouched` override rule as every other auto-suggestion — a manual Severity edit always wins from then on) and prepends `LEAKING_OVERLAY`'s safety-first advisor content (see `workbench/repair-advisor.ts` above) on top of the finding type's own guidance. `WALL_LOSS_TYPES` (4 of the 8 types) is where the numeric B31.3 assessment applies.
- **Dashboard layout** (`#viewList`): `.dash-top` is **two side-by-side panels** — map (flex-grow) and KPI column (`flex: 0 0 340px`) — under a **mutual max-height stretch** (`align-items: stretch` on `.dash-top`; individual KPI cards inside `.kpi-sidebar` stay content-sized among themselves, only the sidebar's *aggregate* height participates in the stretch). `.dash-map-panel` is a flex column: a compact `.panel-h` (title + the `#mapColorBy` select), then `#mapLegend` on its own full-width row below the header (own border, wraps cleanly regardless of palette size — moved out of the header after it visibly crowded/wrapped there), then `#dashMap` (`flex: 1 1 auto`, `min-height: 340px` desktop guard) filling whatever height the stretch gives it. The location map (`#detailMap`) needs `invalidateSize()` after un-hiding. **The Details grid (`renderDetail`'s `d` array, `#detailGrid`) includes a `Pipe Tag / Line` item** (right after Location, matching the form's Terminal → Location → Pipe Tag order) — shows `f.pipe_tag || '—'` explicitly; previously the tag only ever appeared in the sticky header (which falls back to `location_desc`, per the app's location-first identity convention), so a finding *with* a tag set had no way to see it distinctly from Location in the Details panel itself.

**Repair method dropdown** (the "Repaired" status-change dialog, `openStatusDialog`/`confirmStatusChange` in `detail.ts`): `#dlgRepairMethod` is a `<select>` sourced from `REPAIR_METHOD_OPTIONS` (`core/constants.ts` — the PCC-2 category names used by `workbench/repair-advisor.ts`'s numeric REPAIR-status guidance, plus a few non-pressure-repair categories for non-wall-loss types, and a trailing `'Other'`). Picking `'Other'` reveals `#dlgRepairMethodOther`, a free-text field, whose value becomes `patch.repair_method` instead of the select's own value. **Legacy data migration note**: since `repair_method` used to be free text, a saved value that doesn't exactly match one of `REPAIR_METHOD_OPTIONS` is treated as legacy — the dialog pre-selects `'Other'` and prefills the free-text field with the saved value (never silently dropped), so old rows still show correctly and can be normalized to a real category over time (per-user decision — old data is being fixed up manually, not backfilled programmatically).

### Line Risk Ranking (`#/risk`, `#viewRisk`, `src/features/risk.ts`)

A qualitative risk ranking of piping **lines** (not individual findings), rolled up from each line's findings' ASME B31.3 status — deliberately named "Risk Ranking," **not** "POF": there's no real API 581 quantitative POF here (no damage-factor tables, inspection-effectiveness history, or consequence modeling), and naming it POF would risk the numbers being mistaken for a certified RBI figure.

- **Line = `pipe_tag`.** A finding with no `pipe_tag` can't group into a line, so it becomes its own single-finding pseudo-line keyed by `location_desc` (mirrors the tag-fallback convention used everywhere else in the app). `location_desc` and `finding_type` (damage mechanism) both live on the *finding*, not the line — `line_list` has no location or mechanism column at all — so a multi-finding line can have multiple locations **and** multiple mechanisms; both are surfaced honestly (a location count + up to 2 mechanism chips, `mechChipsHtml`), never flattened to one value.
- **Risk band** = worst ASME B31.3 status across the line's assessed findings (REPAIR > MONITOR > OK), re-derived from each finding's *latest* assessment snapshot via `resFromSnapshot()` (`detail.ts` — same function the detail page uses, so the two pages can never disagree). Non-wall-loss finding types (Dent, Coating, Pipe Support Defect, Other) never get a `computeB313` result and sit permanently in a separate **Not Assessed** band — deliberately still shown rather than excluded, since a bad Dent is a real risk even without a numeric wall-thickness score.
- `loadRiskData()` bulk-loads every finding's assessment history in one query (not per-finding like the detail page) and keeps only the latest row per `finding_id` client-side into `riskAssessments` (`core/state.ts`). `computeLineRisk()` groups+rolls up; sort is band first, then ascending remaining life within a band (lines with no computed remaining life sort last), Not-Assessed always last.
- **Sticky toolbar** matches the Detail page's pattern exactly: `.toolbar-id-row` wraps the back-link + `.risk-toolbar-title` (static text, so — unlike `.detail-head h2` — it does **not** need the `'Noto Sans Thai'` fallback in its font stack) so the page identity and the Terminal filter / "Include repaired / closed" switch stay pinned while the KPI band, charts, and table scroll beneath.
- Two charts, both built from `computeLineRisk()`'s output, no charting library: `renderRiskTerminalChart` (stacked bar per terminal, band composition) and `renderRiskMechanismChart` (bar per damage mechanism, High-risk lines only) — the mechanism chart's bar colors come straight from `TYPE_COLORS`, so a `TYPE_COLORS` change (see `core/constants.ts` above) reflects here and on the dashboard map automatically, never a second palette to keep in sync.
- The ranked table's rows are collapsible: a multi-finding line renders one summary `<tr class="line-row" data-line-key="…">` followed by its (initially `display:none`) `child-row`s, toggled open/closed on click. The summary row's `.expand-caret` is **always** rendered in the markup (just `visibility:hidden` on single-finding rows) — omitting it entirely on single-finding rows left their tag text ~19px left of multi-finding rows', breaking column alignment down the table; keep this "reserve the slot, hide the content" pattern for any future column that's conditionally present per-row.

### Quick calculator (`#/calc`, `#viewCalc`)

A standalone what-if workbench — **nothing loads, nothing saves**. Its own small input set (`q`-prefixed ids) + own `paCreateAssessView` instance (`#awQuick`), deliberately independent of the finding form. **No Repair Advisor panel here** (Quick Calc has no finding type to key advice off, and is intentionally isolated). Wired in `initQuickCalc()`. Reached from the header's "Quick Calc" button. Toolbar also has **Copy Summary** (clipboard text) and **Export PDF** (`#btnQuickPdf` → `exportQuickPdf()` → `pdf.ts`'s `buildQuickCalcPdf(inputs, res)`), both disabled-by-guard when `lastQuickRes` is null (no valid calculation yet).

**Quick Calc PDF** (`buildQuickCalcPdf`, `pdf.ts`): a standalone report in the same visual system as the unified finding PDF (chrome, navy section rule, status-color band, `table.list`-style autotables, real stacked-fraction equations) but **never mistakable for a recorded finding** — title reads "ASME B31.3 QUICK CALCULATION REPORT" (not "…FINDING REPORT"), the DOC REF is keyed off NPS + timestamp (no finding id exists), and a bordered amber disclaimer band right under the header states plainly that this is a scratch what-if calculation and no finding/assessment record was created or saved. Content: disclaimer → Integrity Status band → Calculation Input Parameters (NPS/schedule/material/etc., sourced from the Quick Calc form's own fields, passed in via the caller's `inputs` object since `pdf.ts` has no access to `#/calc`'s DOM ids) → Wall Thickness Cross-Section figure → Calculation Results (PASS/CHECK) → Governing Equations (Substituted) → Scope & Limitations. No finding-specific sections (no photos, site map, status history, or audit stamp — there's no finding to audit). The **results table, equation rows, fraction-drawing, and PASS/CHECK cell styling are shared with `buildFindingPdf`** via top-level exports (`buildResultsTableBody`, `buildEquationRows`, `drawFractionRow`, `fractionRowHeight`, `resultsTableDidParseCell`) — same computeB313 result shape (`B313Result`) feeds both reports, so a REPAIR-status finding and an equivalent Quick Calc scenario render byte-identical numbers/equations; only the surrounding chrome/sections differ. Keep new results/equation rows in these shared functions, not duplicated per report.

### Unified finding PDF (detail toolbar "Export PDF")

`buildFindingPdf()` is one report for both finding record and assessment. Chrome: `M`=14/`HEADER_H`=18/`FOOTER_H`=16, logo-left/navy-title-right header, page-x-of-y footer, `— End of Report —` marker. Fonts: GoogleSans + courier for numerics.

**Professional / engineering-document design (redesigned from the earlier "Word-template" look):**
- **Numbered section headers** via the shared top-level `drawSectionHeader(doc, num, title, x, y, right)` — a solid navy number chip + navy title + full-width navy rule. Used by **both** `buildFindingPdf` and `buildQuickCalcPdf` (each keeps its own `secNum`/`figNum` counters and its own `section()`/`ensure()` closures for page-position state) so the two reports stay one visual family. `section(title, minBodyHeight)` auto-increments `secNum` and reserves header + `minBodyHeight` of body via `ensure()` for **orphan-heading control** (a heading never lands alone at a page foot) — never hardcode a section number.
- **Summary block = health banner + identity grid + QR** (replaced the old three rounded gradient "dashboard cards", then the flat 2×4 verdict grid): the top element is a **full-width color-filled "integrity health" banner** — the at-a-glance hero so a quick reviewer reads healthy/unhealthy from the band color before any detail. Band reflects the **engineering health** (ASME B31.3 verdict / leaking / finding type), not workflow, with a plain-language line on the left and (when assessed) `ERF · MAWP · % wall` metrics on the right. States: green `INTEGRITY: OK` / amber `MONITOR` / red `REPAIR REQUIRED` / red `LEAKING` for numeric verdicts; then the no-numeric-verdict cases are split three ways so a non-wall-loss finding is never mislabeled "no data": **blue `ACTION REQUIRED`** ("Requires remediation — see the Repair Advisor…") for a **non-wall-loss finding type** (Coating, Support, Dent, Other — the wall-loss calc doesn't apply but the finding still needs action; blue deliberately stays out of the green/amber/red numeric palette so it implies no fake numeric verdict), grey `PENDING ASSESSMENT` for a **wall-loss type with no reading yet**, and grey `NOT ASSESSED` only when there's **no finding type at all**. Fills are 700-tier shades (`#047857`/`#b45309`/`#b91c1c`/`#475569`) with a darker left spine so white text clears WCAG. **The banner logic is `resolveIntegrityBanner(finding, res)` in `workbench/assess-view.ts` — shared with the web detail page's own top-of-page banner (`#detailHealthBanner`, `renderHealthBanner` in `detail.ts`, `.health-banner`/`.hb-*` CSS in `theme.css`)**, so the PDF and the live page can never disagree on wording/color/state for the same finding. Below the banner: a neutral bordered 2-row × 4-cell identity grid via the local `tbCell` helper — Line Tag · Terminal · Finding Type · Severity / Report Ref · Finding Status (colored dot, OVERDUE red tag) · Inspection Date · Recorded By — narrowed to make room for the **QR code** (top-right, see the public-share bullet above) when one was generated; grid falls back to its full former width if the QR failed to generate. **Report Ref / DOC REF is built by `docRefSlug(tag)`** (shared by `buildFindingPdf` and `buildSlidesPdf`, both format `PA-RPT-<slug>`) — disallowed characters (e.g. the `"` inch-mark in a tag like `906100-8"-D3101-N`) are **dropped**, not replaced with `_`, then repeated/edge dashes are collapsed/trimmed; a naive char-for-char `_` replace was the original approach and produced a stray underscore (`906100-8_-D3101-N`) that a user flagged as visually wrong. Workflow status (Open/Overdue) lives in the grid, health in the banner — deliberately separate concepts. **When leaking, the banner IS the leaking notice** (red `INTEGRITY: LEAKING` + emergency-containment line) — there is no longer a separate "ACTIVELY LEAKING" red bar under the block (it was a duplicate; removed). Leaking is still detailed by the Repair Advisor's leaking overlay + the ASME B31.3 Integrity Evaluation Note.
- **Integrity-status band**: a flat light-tint callout (`#ecfdf5`/`#fffbeb`/`#fef2f2`) with a solid colored left spine + dark semantic bold text (`#15803d`/`PDF_WARN_MID`/`#b91c1c`) + ERF/MAWP/MARGIN metrics right-aligned — an engineering callout, not a saturated web-card fill. Same treatment in the Quick Calc PDF's Calculation Result band.
- **No signature/approval block** — this is a **paperless system**, so there is deliberately no "Document Control & Approval" or wet-signature section (an early redesign added one, then removed it at the user's request). Both PDFs close with a restrained **system-generated record footnote** (a hairline rule + "paperless … no physical signature required" + attribution / timestamp) then the `— End of Report —` marker: the finding report's footnote carries recorded-by + Record ID `PA-<id>`; the Quick Calc PDF's is adapted for the scratch what-if (no Record ID, re-states "Not a recorded finding"). Don't reintroduce a signature grid.
- `PDF_NAVY_TINT`/`PDF_PANEL` are neutral-fill constants available for these blocks (kept even though the current layout inlines its tints).

Content order: **title block** → Piping Metadata & Source Inspection → Anomaly & Damage Mechanics → **Repair Advisor** → Site Location → Photographic Record → **assessment block** (only when a snapshot exists *and* re-computes): integrity-status band → Assessment Input Parameters autotable → Wall Thickness Cross-Section figure → Calculation Results autotable → Governing Equations with real stacked fractions → Scope & Limitations → Status History → **system-generated record footnote**. A legacy snapshot that can't re-compute falls back to a compact saved-results section.

**Repair Advisor section** (placed right after Anomaly, so "recommended action" reads directly after the problem while the numeric verdict is already shown in the page-1 title block — matching the web detail page's Details → Repair Advisor → Assessment order): **always rendered, never gated on an assessment existing** (the earlier CLAUDE.md claimed this but the code never actually rendered it — `resolveAdvisor` was an unused import until it was wired in). Built from `resolveAdvisor(f.finding_type, assessRes, f.is_leaking)`, mirroring `paRenderRepairAdvisor`'s status/leaking precedence: a colored banner callout (same light-tint + colored-spine language as the integrity band — REPAIR/leaking red, MONITOR amber, OK green, else navy "ASME PCC-2 / API 570 GUIDANCE") + the Thai `summary`, then a title/body autotable of the resolved `items` (navy-bold label column like the metadata tables; each item's `sub[]` points become `•`-bulleted lines in the body cell), then the `standardsNote` + `needsReview` caveat as an italic footnote. Status- and mechanism-aware, leaking-overlay safety block prepended when `is_leaking`. Thai prose keeps English technical nouns (Composite, Welded, WPS/PQR, Pre-heat, NDT, Cathodic Protection, etc.) — same split as the web panel.

Numbers are **re-derived from saved inputs through `computeB313`**, so PDF and web UI can never disagree. All images are pre-awaited before drawing. Semantic colors are named constants (`PDF_OK`/`PDF_WARN`/`PDF_DANGER`/`PDF_NAVY`/etc.) — never re-type hex per call site. **Only WinAnsi-safe characters** in PDF strings (no `≥`/`≤` — use `>=`/`<=`). Export uses the `blob:`-anchor native-viewer approach — never `window.open`+`.location` or `data:` URLs.

**Font-size type scales**: every `setFontSize()` call across all four PDF builders (`buildFindingPdf`, `buildQuickCalcPdf`, `buildSummaryPdf`, `buildSlidesPdf`) goes through named `const FS_*` constants declared near the top of that function — **no bare numeric literal appears anywhere in any of the four**. Each function has its **own locally-scoped scale** (not shared across functions — these are visually distinct documents: A4 portrait report, A4 portrait quick-calc, A4 landscape register table, 16:9 presentation slide), following the same naming pattern (`FS_MICRO`/`FS_LABEL`/`FS_BODY`/`FS_VALUE`/`FS_TITLE`/`FS_HERO` etc., with a couple of function-specific extras like `FS_CAPTION`/`FS_DISCLAIMER`/`FS_SUMMARY` where a genuinely distinct role exists). This consolidated ~44 near-duplicate ad hoc sizes total (11 in `buildFindingPdf`, 8 in `buildQuickCalcPdf`, 7 in `buildSummaryPdf`, ~18 in `buildSlidesPdf` before its own earlier pass) down to under a dozen named roles per function — accumulated over many rounds of "make it bigger"/"make it smaller" edits with no scale discipline. **One exception is deliberate, not an oversight**: `buildFindingPdf`'s `tbCell` identity-grid helper (the top-of-report Line Tag/Terminal/Finding Type/Severity/Report Ref/Status/Inspection Date/Recorded By grid) keeps a per-call `opts.fs` literal override (8.5/8/9.5/9/7.5) — these are tuned per grid cell to fit that specific cell's content width (e.g. short "Severity" gets a larger size, longer "Finding Type" gets a smaller one so it doesn't wrap awkwardly), not meaningless near-duplicates, so don't try to collapse them into one shared constant. When adding a new label/value anywhere in any of the four builders, reuse an existing constant for that role rather than typing a new number — a fresh literal is exactly how the sprawl reappears.

## Running / testing

- `npm run dev` for local development; full function needs a network connection (Supabase).
- **Automated suite is just the one Vitest file** (`compute.test.ts`, the parity gate). Everything else is verified with **ad hoc Playwright scripts written to the session scratchpad** — not checked into the repo, recreated per verification pass. Pattern established across many sessions: sign in with real credentials (never hardcoded/committed — supply via env vars or ask the user), exercise the feature in-browser, assert on rendered DOM/PDF content, then clean up any test finding created (clearly tagged, e.g. `TEST-E2E-...`, deleted at the end of the script).
- Headless Chromium does not paint iframe PDF viewers — verify generated PDF *content* by exporting the blob bytes and reading them with `pdfjs-dist` (`legacy/build/pdf.js` build works outside a browser) rather than a DOM screenshot.
- For anything touching saved data or PDF output specifically, run the authenticated E2E pass described in the extraction-pattern note above before calling a change verified — build/typecheck alone has repeatedly missed real runtime bugs (the Thai `splitTextToSize` bug, an unused-import miss, etc.).

## Conventions to preserve

- Pressure entered in `bar`/`psi`, always converted to **MPa** internally (inside `computeB313`).
- The app has no dark mode — a single light palette only. The app header (`body > header`) is sticky with a thin teal→sky `.header-accent-bar` and the OR logo in a `.hdr-logo-chip`. `syncHeaderHeight()` measures it into `--app-header-h` for anything else sticky. The logo `<img>` carries explicit `width`/`height` attributes to avoid a FOUC/CLS flash on first paint (the browser reserves the box before CSS/the image itself loads).
- Two reading modes (wall-loss depth, listed first / measured thickness) tracked via `.active` on the mode segment buttons; mutually derivable (`t_meas = t_nom − depth`).
- Validation uses `aria-invalid="true"` + `.validation-alert` visibility.
- All numeric display formatting goes through `paFmt(val, decimals)` (`—` for null/non-finite); `fmtN` is the PDF-local equivalent.
- **One font: Google Sans everywhere** (web + PDF) for Latin/numeric text, **Noto Sans Thai** for Thai text (see above) — "Google Sans" is proprietary and not on the public Google Fonts API, so `registerGoogleSansWebFont()` injects an `@font-face` from the same embedded base64 TTFs the PDF uses. Only Regular(400)+Bold(700) exist, mapped via weight ranges. No JetBrains Mono / no Google Fonts CDN link — numerics keep `font-variant-numeric: tabular-nums` so figures still column-align. Dense-engineering styling: hairline borders, `--radius: 0.5rem`, spacing tuned per component in small (~2–4px) increments; border-radius scale **6px** interactive controls / **8px** containers, pills use `height/2`.
- Readability floor: 11px for anything actively read; 10px only for short uppercase badge/eyebrow text.
- **Font-size scale, web UI**: every `font-size:` declaration in `theme.css`/`app.css` resolves to one of 12 `--fs-*` custom properties defined in `theme.css`'s `:root` (`--fs-2xs` 9px through `--fs-hero` 26px) — **no bare px value appears anywhere in either stylesheet** except one deliberately-relative `0.8em` (a `.panel-h h2::after` suffix meant to scale with whatever heading it's attached to, not pinned absolutely). This consolidated 19 raw px values (165 declarations, accumulated over many rounds of ad hoc sizing with no token backing — colors already had `--text-color`/`--text-muted`/`--text-light` tokens, font-size didn't) down to 12 named roles. `--fs-2xs` (9px) sits one step below the 11px readability floor and is scoped **only** to short uppercase badge/eyebrow chips or single glyphs (kbd hints, compact status pills, close-icon glyphs) — never body prose, consistent with the floor's own stated exception for short badge text. The KPI/heading cluster (`--fs-xl` 15px / `--fs-2xl` 16px / `--fs-3xl` 17px / `--fs-4xl` 18px / `--fs-5xl` 20px / `--fs-hero` 26px) is kept as six separate steps **on purpose, not merged** — several sit side by side in the same card (e.g. the KPI ring's 17px percentage next to its 15px fraction), forming a real, deliberate visual hierarchy that collapsing would visibly flatten. When adding a new rule anywhere in either stylesheet, reuse an existing `--fs-*` token for that role rather than typing a raw number — a fresh literal is exactly how the sprawl reappears (same lesson learned consolidating the PDF builders' `setFontSize()` calls, see `features/pdf.ts` below).
- Semantic status colors (`--ok-color`/`--warn-color`/`--danger-color`) and cross-section limit colors (`--limit-*`) are CSS variables — never hardcode their hex in CSS/SVG attributes. The `--limit-*` values are dark 700–800-tier shades so 11px bold SVG labels clear WCAG AA against `--svg-bg`; the PDF renders via `paSvgToPng`'s injected style block, which duplicates this hex list as static values (CSS vars don't resolve in a standalone serialized SVG) — keep it in sync. `STATUS_COLORS`/`TYPE_COLORS`/`SEVERITY_COLORS` (`core/constants.ts`) are likewise fixed hex, deliberately theme-independent (drawn over satellite imagery, whose background never changes with app theme).
- The universal `* { transition: … }` rule in `theme.css` is the single source for state-change fades; components only declare their own `transition` for properties it doesn't cover.
- CSS cascade-order trap: an override placed *earlier* in the stylesheet than the base rule it targets, at equal specificity, silently loses (source order wins) — scope overrides tighter instead of relying on media-query placement alone.
- SVG/XML comments must never contain `--` (breaks `XMLSerializer` for the PDF export path), and JS block comments must never contain `*/` mid-text.
- **Content that should get domain-expert review**: `workbench/repair-advisor.ts`'s non-wall-loss guidance entries and `LEAKING_OVERLAY` are flagged `needsReview: true` in code — they're defensible drafts grounded in real standards (SSPC/NACE, API 570/579-1/583, PCC-2 Parts 3/4/6) but not verified by a domain engineer. Treat as shippable general guidance, not as settled/authoritative content to build further automation on top of without a review pass.
