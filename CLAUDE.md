This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Rules

- **Do NOT push to git automatically**: Never run `git push` after code edits unless the user explicitly requests a push. The user prefers to review changes locally and push manually.

## What this is

Pipe Assessor is a **Vite + Vanilla TypeScript** (no framework) single-page app: the Findings Tracker dashboard — a Supabase-backed register of abnormal piping inspection findings tracked from Open until repaired/closed, with a full **ASME B31.3** wall-thickness assessment workbench built in. The workbench evaluates required thickness / MAWP per ASME B31.3, checks API 574 structural minimums, and — via the standalone **Repair Advisor** — gives repair guidance per ASME PCC-2 (or the applicable standard for non-wall-loss damage). A field engineer enters the measured wall loss and gets a live status (OK / MONITOR / REPAIR), cross-section diagram, results table, repair advisor, substituted equations, remaining-life estimate, and a generated PDF engineering report. The whole app requires sign-in and a network connection (Supabase); offline it degrades to a login screen with a "check your connection" notice.

**History note:** this was originally a no-build single-file monolith (`index.html` + three classic-script `asset/*` files), then a standalone calculator (`calculator.html`) merged into the dashboard. Both migrations are complete and merged to `main`. Git history retains both prior forms if archaeology is ever needed; nothing below describes them further.

## Module map (`src/`)

- **`engine/`** — the ASME B31.3 engine, **strictly typed** (no `@ts-nocheck`): `compute.ts` (`computeB313` + re-exports), `pipe-data.ts` (`PA_PIPE_DATABASE`/`PA_MATERIALS`, extracted verbatim from the pre-migration `shared.js`), `format.ts` (`paFmt*`), `fonts.ts` (base64 Google Sans + `registerGoogleSansWebFont` for the web; `registerGoogleSansFonts` — async, loads Sarabun — for the PDF; see Thai text below), `branding.ts` (`OR_LOGO_DATAURL` + `downscaleImage`).
- **`legacy/shared.js`** — **frozen, not live code.** The pre-migration classic-script file, kept only as the baseline `compute.test.ts` diffs against (evaluated in a VM sandbox; `computeB313` must be bit-identical across a large size/schedule/material/mode/override matrix — must stay 0 mismatches). Never edit it and never import it from app code — to change the engine, change `engine/compute.ts` and update the parity test's expected divergences instead.
- **`workbench/`** — the ASME B31.3 result-display layer and the repair-advisor content, both strictly typed:
  - `assess-view.ts` — `paCreateAssessView(root, opts) → view`: injects the workbench markup into `root`, returns `{ render(res, ctx), getSvg(), getLastRes() }`. `opts.sections` picks blocks in order from `status | scope | svg | results | equations` (no `advisor` entry any more — see below); `opts.collapsed` lists sections rendered as closed `<details>`; `opts.onDepthDrag(depth_mm)` enables the SVG drag handle (omit for read-only views). `render(res, ctx)` takes a `computeB313` result (or `null`) and `ctx = { neutral, nps }` — `neutral: true` shows the grey "enter data to begin" banner instead of a red ERROR. Markup carries no element ids — every lookup is `data-k` scoped to the instance root, so multiple instances coexist in one document (form, detail page, quick calc). **Cross-section figure design (Oct 2026)** — hand-written SVG on purpose (chart libraries/D3 were considered and rejected: it is an engineering diagram, not a chart, and it must rasterize through `paSvgToPng` for the PDFs). It answers one question first: a **verdict-coloured dimension bracket** from the thinnest point (the drag handle) to the **deciding limit** = the higher of `t_req + CA` (REPAIR below it) and the API 574 minimum (MONITOR below it), labelled "N mm above limit" / "N mm below limit" (`paLimitGap`). It can differ from the results' "Vs. min. + CA" row (`margin`, measured to `t_req + CA`) whenever API 574 decides. The deciding line is drawn bold with a full-colour "· decides" label; the other limits are thin and muted. Palette: the wall is a **steel gradient** (`paXsMetal`, light at the outside surface → darker at the bore) and the lost metal is **rust** (`paXsLoss`, pale at the original surface → darkest at the deepest point; `drawSvg` flips it for internal loss) — green/amber/red stay reserved for the verdict bracket. Both are literal-hex `<linearGradient>`s (so they survive `paSvgToPng`) whose ids are made unique per instance — a gradient inside a hidden view would not paint for the other instance. The old `--svg-metal`/`--svg-loss`/`--svg-loss-border` tokens are gone (theme.css and the raster palette list). Two-line labels (name / bold value) sit at their true heights with collision spacing; a mm ruler on the left uses the same origin as the limits (inside surface for external loss, outside surface for internal). **No legend** — one `.aw-svg-note` line instead ("Rust-coloured area = metal lost · …"). The viewBox stays 500×270 because the finding PDF and slides place the image at that aspect ratio. The drag handle is neutral dark (colour belongs to the verdict). Also exports `PA_SCOPE_HTML`/`PA_SCOPE_TEXT` (Scope & Limitations text) and `paSvgToPng`/`paCrossSectionPng` (SVG→PNG rasterization for the PDF figure — injected fixed light-palette `<style>` must stay in sync with `theme.css`'s `--svg-*`/`--limit-*` values; never put `*/` inside a JS block comment in this area, it terminates the comment).
  - `repair-advisor.ts` — the **standalone Repair Advisor**, independent of (not nested inside) the B31.3 assessment panel, so it's always available regardless of finding type. `REPAIR_ADVISOR_BY_FINDING` is a per-finding-type content table (Coating, Pipe Support Defect, Dent, Other — each entry flagged `needsReview: true` since the guidance is a best-effort draft, not verified domain expertise). `resolveAdvisor(findingType, res, isLeaking?) → ResolvedAdvisor | null` is the precedence resolver: wall-loss types (`WALL_LOSS_TYPES`) with a valid non-error `res` get precise numeric advice (`paAdvisorItems(res, findingType)`) that is both **status-aware** (OK / MONITOR / REPAIR) and **mechanism-aware** — `corrMechOf(findingType)` + the `CORR_MITIGATION` table give External / Internal / CUI / CUS corrosion each their own remediation (external removal+recoat+CP vs. internal process-side control vs. CUI insulation/weatherproofing restoration vs. CUS support-detail fix); at OK it still calls out arresting the live corrosion (removal → recoat), and at REPAIR it **always** offers Replacement / Spool Replacement (not only above 80% loss). The numeric base carries `NUMERIC_STANDARDS_NOTE` + `needsReview: true`. Wall-loss types without a valid `res` get a generic "record a reading" prompt; non-wall-loss types always use their own table entry regardless of any stray `res`. `LEAKING_OVERLAY` is a separate safety-first content block (Immediate Safety / Root Cause / Interim Containment / Spool Replacement) **prepended** to whatever the base entry resolves to when `isLeaking` is true — Leak is **not** a finding type (see `core/constants.ts` below), it's an orthogonal flag any finding can carry. `paRenderRepairAdvisor(root, findingType, res, isLeaking?)` renders into a plain container — one panel, mounted independently in the form (`#raBody`), the detail page (`#raDetailBody`), and threaded into the PDF's "Repair Advisor" section (always renders, not gated on an assessment existing). **Advisor prose (summaries/body text) is in Thai**, but the panel title stays **"Repair Advisor"** in English, and **technical nouns inside the Thai text stay in English** too — material/method/equipment/standard terms like Composite, Epoxy, Mechanical Clamp, Pre-heat, NDT, WPS/PQR, Coating, Gouge, Sleeve, Support, Shoe, Hanger Rod are left untranslated (transliterating them into Thai script reads worse to a Thai engineer than the English term itself). Code comments and identifiers stay English throughout. Keep this split when editing — narrative sentences in Thai, technical terms in English, panel chrome/title in English.

**Extraction pattern**, if splitting a feature module further: (1) identify a block's true dependencies with an identifier scan against `core/`/other features; (2) extract with a small Node script (never hand-copy — base64 font/logo blobs break line-based tools, and hand-editing thousands of lines invites transcription bugs); (3) **validate with the TypeScript name-resolution guard** — temporarily strip the touched files' `@ts-nocheck` banners and set `strictNullChecks:false` in `tsconfig.json`, run `tsc --noEmit`, and grep for `TS2304` (missing name) / `TS2305`/`TS2307` (missing export/module) / `TS2540`/`TS2539` (illegal reassignment of a read-only import — the live-binding-state trap) / `TS2300`/`TS2451`/`TS2440`/`TS2448`/`TS2454` (redeclaration) / **`TS2552`** (a *near-miss* unresolved name — "Cannot find name X, did you mean Y?" — easy to miss if only grepping TS2304; caught a real bug where `pdf.ts` imported `paFmtDateTime` but the ported body called `fmtDateTime`, the `core/dom.ts` alias); restore the banners after. Run this after every extraction, not just at the end. (4) `npm run test` (parity) + `npm run build` (also confirms lazy chunks stay lazy) + a Playwright smoke test against the dev server or `npm run preview`. (5) **For anything touching saved data or PDF output, a generic smoke test is not enough** — a structurally-clean build can still have runtime bugs invisible to typecheck/build (e.g. a jsPDF text-measurement function like `splitTextToSize` silently mis-measuring Thai glyphs because it ran under the wrong active font at call time — not caught until an authenticated E2E test rendered a real PDF from real saved data and the text was visibly missing). Run an authenticated E2E pass (sign in with real test credentials, create → save → view detail → export PDF → delete a clearly-tagged test finding) before considering a change fully verified.

**Circular imports are sometimes correct here**: e.g. `form.ts` imports `show` from `../app` (the router's view-switcher genuinely lives in the hub) while `app.ts` imports form functions back — safe specifically because both sides are `function` declarations (hoisted), never `const` arrow functions, so the cycle resolves at call time, not at module-eval time.

**Thai text**: the web app and the PDF report use **different fonts for different reasons**, so don't assume changing one changes the other. Web: Google Sans has no Thai glyphs, so `'Noto Sans Thai'` sits right after `'Google Sans'` in the `html, body` font stack (`theme.css`), imported via `@fontsource/noto-sans-thai` at weights 400/500/600/700 in `main.ts`; its `@font-face` rules are `unicode-range`-scoped to the Thai block (`U+0E01-0E5B`) so it never touches Latin/numeric rendering — the browser's normal per-character font fallback does the rest. PDF: the report uses **Sarabun** (`https://fonts.google.com/specimen/Sarabun`, OFL-1.1) instead of Google Sans — chosen specifically because it natively covers **both** Latin and Thai glyphs in one face, so unlike the web split above there's no font-switching needed: `registerGoogleSansFonts(doc)` (`src/engine/fonts.ts`, now **async**) fetches `src/assets/fonts/Sarabun-{Regular,Bold,Italic,BoldItalic}.ttf` (sourced from the google/fonts OFL repo) as lazy Vite `?url` assets and registers all four faces under the jsPDF font name `'GoogleSans'` — deliberately kept as that name (not renamed to `'Sarabun'`) so the ~90 existing `doc.setFont('GoogleSans', …)` call sites across both PDF builders don't need to change. There is no more Thai-detection monkey-patch (`registerThaiPdfFont` is gone) — every `doc.text()`/`doc.splitTextToSize()` call renders correctly regardless of script, since it's one font for the whole document.

## Findings Tracker / Dashboard (`index.html` + Supabase)

The app's landing page and primary daily tool: a register of **abnormal findings** from vendor inspection reports, each tracked through a status lifecycle until repaired — the design goal is "no finding is ever forgotten." Deliberately finding-centric: there is **no pipe-asset register or CML/TML model** (the pipe tag is a plain field on the finding, with autocomplete from previously entered tags plus the master line list below); don't add one without the user asking.

**Location-first identity**: the app serves operators (who know *where* a problem is, not the Line No.) as well as engineers. So **Location Description is the required identity field and Pipe Tag / Line No. is optional** (`pipe_tag` is nullable — an engineer assigns the Line No. later). Everywhere a finding is labeled by its tag — register row, map popup, detail `<h2>`, both PDFs' tag column/header — it **falls back to `location_desc` when `pipe_tag` is empty** (`f.pipe_tag || f.location_desc || '—'`). (The findings **bulk import** still requires Pipe Tag — an engineer batch path, intentionally not changed.)

- **Backend**: Supabase project `uuwcftjduphtngmhwvrb` (**Singapore** region), URL + `sb_publishable_` key in `src/core/supabase.ts` — safe to commit; every table is RLS-gated to the `authenticated` role, **except the one public RPC described below**.
- **`db/schema.sql`** is the single source of truth for the database — idempotent, applied by pasting into the Supabase SQL Editor. Tables: `findings`, `finding_photos` (`kind` ∈ `found`|`repaired`|`temp_before`|`temp_after`), `status_history` (the handover trail), `assessments` (workbench snapshots: `{ inputs, results }`), `line_list` (the master pipe-tag reference — see below), `temp_repair` (the emergency stop-leak record — **section 7a**, mirrored standalone in `db/temp-repair-migration.sql`; placed before section 8 because `get_public_finding` selects from it), and `inspection_plan` + `plan_task` (the scheduling module behind `#/plan` — **section 10**, mirrored standalone in `db/inspection-plan-migration.sql`). **Status values are a check constraint AND a JS array (`STATUSES`)** — `'Open','Monitoring','Repair Planned','Repaired','Closed'` must match exactly in both places. `findings.estimated_cost numeric` (nullable) holds the manual repair-cost estimate; `findings.is_leaking boolean not null default false` is the "Actively Leaking" flag (see below). **`findings.depth_mm numeric`** (nullable, `>= 0`) is the measured wall-loss depth at the deepest point — the operator's field reading, saved with or without a Line No. / pipe size / pressure (see the form section); mirrored standalone in `db/depth-migration.sql`. **Adding a column to an existing DB requires an explicit `alter table … add column if not exists`** (see the patches near the top) — ship the migration before the code that writes the column, or every save fails with PostgREST 42703. `line_list` is created *before* section 6's RLS block (not appended at the very end) since that block enables RLS on it — keep that ordering if the file is restructured. **Section 8** is the public-share RPC (`get_public_finding`, see below) — also mirrored standalone in `db/public-share-migration.sql` for a one-off paste if section 8 alone hasn't been applied yet.
- **Auth model**: email/password only. **Self-registration is open but domain-restricted** to `ALLOWED_SIGNUP_DOMAINS` (`core/constants.ts` — `pttor.com`, `pttplc.com`), auto-approved as `inspector`. The real gate is the `pa_enforce_signup_domain` trigger on `auth.users` (schema §9); the client-side check in `signUp()` only produces a friendlier message. **Supabase Auth must have "Confirm email" ON** — with auto-approval the email domain *is* the access control, so without confirmation anyone could register as `someone@pttor.com` without owning that mailbox. Audit is the `*_email` columns defaulted from `auth.jwt() ->> 'email'`. The `onAuthStateChange` handler re-routes **only when signed-in state flips** — routing on `TOKEN_REFRESHED` would re-render mid-edit and wipe unsaved form input — and `loadProfile()` runs *before* `route()` on a flip so the first paint already has the right role chrome (a later fetch would briefly show maintenance-only controls to an inspector). **The callback body is deferred via `setTimeout(...,0)`, not run directly** — a real production incident shipped without this: supabase-js/gotrue-js holds an internal lock while dispatching `onAuthStateChange`, and any Supabase call awaited synchronously inside the callback (`loadProfile()`'s `sb.from('profiles')...`, or `route()`'s finding/line-list queries) needs that same lock to attach the session's Authorization header — deadlock. The call never resolved *or* rejected, so nothing ever threw; no `.view` ever got `.active`, leaving the page permanently blank below the header/footer (which aren't view-gated, so they still rendered — this is why the failure looked like "the page is empty" rather than an error). It reproduced **only** on a page load that restores an already-persisted session (`SIGNED_IN`/`INITIAL_SESSION` firing during the client's own startup, while the lock is still held) — a fresh interactive sign-in fires the event well after startup with the lock already free, which is exactly why the roles feature's E2E pass never caught it: every test signed in fresh each time and never reloaded an already-authenticated tab. Deferring with `setTimeout(...,0)` runs the callback body in a new task after the dispatch (and its lock) has finished — the standard workaround for this known supabase-js gotcha. **Any future code added inside this callback must stay inside the `setTimeout`**, not before it.

### Combined finding form + full assessment workbench (`#viewForm`)

The first panel's own `<h2>` is a static "Finding Info" label, not the dynamic title (that used to double as both, but a scrolled-away title on a 7-panel form was the actual bug this fixed).

ONE column (`.form-flow`, max 1280px, centred) with section links in the sticky header (`#formSectionNav`, see Main menu). **Section order is ONE sequence shared by the finding form, the detail page and the finding PDF** — Location → Anomaly → Photos → Temporary Repair (only when leaking / recorded) → Line Identification → Reference & Planning → ASME B31.3 Assessment → Repair Advisor (→ Status History on detail + PDF). The Line Identification header's **"Manage line list"** (`#btnLineList`) — now an `<a href="#/lines" target="_blank">`, **deliberately opening in a new tab**: it used to be a dialog that overlaid the form so a half-entered finding survived, and once the line list became a page, navigating in place would have silently discarded unsaved form input. Last two sections: the **ASME B31.3 Assessment panel** (`#assessPanel`, toggled `.on`) — pipe-setup inputs (`a`-prefixed ids: `aNps`/`aSch`/`aMat`/`aTnom`/`aTmeas`/`aDepth`/`aP`/…, default material `API5LB`; `aCa` sits with the design params, not the reading section), then the **full live workbench** (`awFormView = paCreateAssessView($('awForm'), …)` — status banner, cross-section with working drag handle, compliance verdicts, ERF gauge, results grid, equations collapsed, scope notice — **no advisor section**), then the standalone **Repair Advisor panel** (`#repairAdvisorPanel`, always visible, independent of `#assessPanel`'s toggle — see `workbench/repair-advisor.ts` above). One Save records the finding *and* its assessment snapshot.

Behaviors to preserve:
- **Auto-enable** when `fType` ∈ `WALL_LOSS_TYPES` (unless the user toggled manually — `assessToggleTouched`); **Corrosion Type auto-follows the Finding Type** (`CORR_TYPE_BY_FINDING`; CUI/CUS are external) **and is locked (`disabled`) whenever the type decides it** — editable only for types that don't (Dent/Other assessed manually); a saved snapshot's `corr_type` is restored only in that case.
- **No double entry** (from a form-duplicates audit): temp-repair **Tested At** is one field (`tested_at`) drawn as date + 24h HH:mm text box on one row — deliberately NOT a `datetime-local` (shows AM/PM on many phones); the temp-repair **perm_method / perm_target_date pre-fill** the status dialog's Repaired method / Repair Planned date (and the form's maintenance-only Target Repair Date when empty) — never overwriting a value already set; pasting `"lat, lng"` into either coordinate box splits it and drops the pin (paste handler, since a `type=number` box rejects comma text). "Installation Method" was renamed **"Installation Procedure / Notes"** (form + `tempRepairRows`) — it read as a duplicate of "Repair Method".
- `recalcAssessment()` runs the shared `computeB313` live on every input, renders through the workbench, **and calls `renderRepairAdvisor()`** so the standalone advisor stays in sync with both the finding type and the live numeric result. **Neutral-vs-invalid rule**: required-but-empty fields show the grey neutral banner; only actually-invalid typed input shows the red ERROR banner + a targeted message in `#aCalcHint`. (`CA ≥ t_meas` is not an error — only `ca < 0` is.) The **CA input lives with the design parameters**, not the reading section.
- **A blank UT reading means "not entered", never "0 mm lost".** `computeB313` (parity-locked, so not changed there) reads a blank wall-loss depth as 0 — that used to show, and SAVE, "OK / 100% wall left / pressure use 11%" for an unmeasured pipe (4 of 25 saved snapshots in Oct 2026, one on a leaking finding whose banner then read LEAKING beside "100% wall left"). Now: `aReadingEmpty()` (true when `#fDepth` is blank) makes `recalcAssessment` (and Quick Calc's `recalcQuick`) render the neutral banner with no result; `collectAssessment` returns null when the reading is blank **or the finding is actively leaking**; `snapshotHasReading(a)` (`workbench/assess-view.ts`) filters reading-less rows out of every display load (detail `loadDetail`, public `loadPublicFinding`, `risk.ts`, the slide deck's bulk load) and `resFromSnapshot` refuses them — the old rows stay in the table but show as "no assessment". **Leaking findings never show B31.3 numbers**: `resolveIntegrityBanner` returns `metrics: null` for the leaking state, and the detail Assessment panel shows the same "calculation disabled for actively leaking piping" notice the finding PDF prints.
- **Severity auto-suggests** from status (OK→Low/MONITOR→Medium/REPAIR→High) until the user sets it (`severityTouched`) — and separately from the Actively Leaking checkbox (→High), same touched-flag gate, see above.
- **One reading: the wall-loss depth, entered in Anomaly (`#fDepth`).** Localized corrosion is the governing damage, so the finding form records depth only — the old Wall-loss depth / Measured thickness toggle (`#aModeSeg`, `aDepth`, `aTmeas`) is gone from the form; the assessment shows a read-only "Wall-loss depth used" line (`#aDepthRef`, `syncDepthRef()`) with a link back to Anomaly, and the SVG drag handle writes `#fDepth`. `aMode()` always returns `'depth'` and the snapshot `inputs` keep their `mode/depth/tmeas` shape (`mode:'depth'`, `tmeas:''`). An older finding opened for edit gets `#fDepth` from its latest snapshot when it has no `depth_mm` (depth-mode snapshot directly; a measured-thickness snapshot converts with that snapshot's OWN pipe size). **Quick Calc keeps its own `#qModeSeg` toggle** (scratch tool, nothing saved). **The pipe size starts blank** (`resetAssessment`, a `Select size…` first option) — a preset 4" looked like a real answer and used to turn an operator's depth into a guessed thickness. Design Pressure is no longer marked required (it is needed for the calculation, not to save), and `#aIntro` says "Don't know them? Save anyway — an engineer completes this later". New findings default Inspection Date to today; GPS shows progress on its own button and one "Location set (±N m)" toast; coordinate placeholders read `e.g. 13.0977`.
- `collectForm` writes **`depth_mm`** from `#fDepth` (validated `>= 0`, `#errDepth`) and **`t_nominal`/`t_measured` only from a complete assessment** (`collectAssessment()` result) — otherwise those keys are OMITTED, so a new finding stores none and an edit never wipes existing values; it never stores a thickness derived from a pipe size nobody chose (the removed `assessThickness()` did). It reads `is_leaking` from the checkbox; `collectTempRepair(id)` snapshots the emergency stop-leak panel (upserted on `finding_id`, or the row deleted when "Installed" is unticked — confirmed before saving, since photos hang off it); `collectAssessment` snapshots `{inputs, results}` — **deduped on edit** via `lastLoadedAssessInputs`. The snapshot `inputs` shape is the long-standing schema (nps/schedule/material/S/E/W/Y/design_temp/P/p_unit/ca/corr_type/cr/mode/depth/tmeas/override_tnom) — saved rows depend on it.
- **Pipe Tag input is a custom searchable combobox** (`initTagCombo`): `#fTag` stays a plain `<input>` wrapped in `.combo` with a floating `.combo-menu`, `position: fixed` (not `absolute` — `.panel { overflow: hidden }` would clip an absolutely-positioned menu to a sliver of the card). Options from `buildTagOptions()` filter on tag OR location, capped at `TAG_COMBO_MAX` (50), scoped to the selected Terminal.
- **Per-tag memory** (`applyTagMemory`, on tag blur when creating): fills empty fields and restores pipe setup from the latest finding on that tag, falling back to `line_list` when the tag has no prior finding. (When it fills design pressure from `line_list.design_p_barg`, the setup object's unit key is `p_unit` — `loadAssessmentInto` reads `inp.p_unit`, not `pUnit`; the old `pUnit` typo was masked only because `bar(g)` is the `#aPUnit` default.)
- **Reset to line list** (`#btnResetAssessLine` in the assessment panel header → `resetAssessmentToLineList`): an explicit button that **overrides** the current pipe setup (NPS / Schedule / Material, plus design pressure + `bar(g)` unit when `line_list.design_p_barg` exists) with the master `line_list` entry for the selected Pipe Tag — unlike `applyTagMemory` it ignores any prior finding's assessment and works while editing too. Keeps the UT reading (`loadAssessmentInto(..., true)` skips depth/t_meas), auto-enables the panel if off, and no-ops with a notice when the tag has no line-list entry.

### Temporary Repair / emergency stop-leak (`#panelTempRepair`, `public.temp_repair`)

The in-app replacement for a standalone Excel form ("รายงานการหยุดรั่วฉุกเฉิน") that maintenance filled in whenever a leak was stopped with a **mechanical clamp or an epoxy/composite wrap**. Deliberately **not** a new page, route, sidebar entry, workflow status, or register column — it is one conditional panel on the finding form, one read-only panel on the detail page, and one conditional section in the finding PDF. **With no record, every one of those surfaces renders exactly as it did before the feature existed** (same PDF sections, same numbering, same page count) — that invariant is the first thing to re-test after touching any of this.

- **`public.temp_repair` (`db/schema.sql` section 7a)** — ONE row per finding (`idx_temp_repair_finding` unique on `finding_id`, so the form saves with `upsert(..., { onConflict: 'finding_id' })`). Unlike `assessments` this is current state, not a dated snapshot; there is no history and no record-level status. **It sits before section 8 on purpose**: `get_public_finding` is a `language sql` function whose body Postgres parses at definition time, so a table it selects from must already exist — same reason `6a. line_list` precedes section 6. Mirrored standalone in `db/temp-repair-migration.sql`.
- **RLS is blanket authenticated (the `assessments` pattern), NOT `line_list`'s write-maintenance.** The panel lives on the same form an *inspector* uses to report the leak in the first place, so gating writes on `pa_is_maintenance()` would make that save fail outright. For the same reason the `finding_photos` insert/update/delete policies were flipped from `kind = 'found' or maintenance` to **`kind <> 'repaired' or maintenance`** — `'repaired'` stays maintenance-only (it is the repair handover), the two new kinds do not.
- **`finding_photos.kind` is now four values** — `'found' | 'repaired' | 'temp_before' | 'temp_after'` (check constraint + `PhotoKind` in `types/models.ts` + `PHOTO_KIND_LABEL` in `detail.ts`, which is what the cap message and the lightbox caption read so a new kind can never leak its raw column value into the UI). `PHOTO_LIMIT_PER_KIND` (4) is per kind, so a finding with a stop-leak record can hold 16 photos rather than 8.
- **Excel section 1 stores nothing.** All seven of its rows already exist: 1.1–1.3 → `pipe_tag`/`location_desc`, 1.4 → `finding_type` + `description` + `is_leaking`, 1.5 → **`findings.service`**, 1.6 → the latest assessment's `P`/`p_unit`/`design_temp` (printed **labelled as design values** — the app has no operating-condition field and does not invent one), 1.7 → `sap_notification`/`sap_order`. The form therefore asks for none of it and the report reads it through. Do not add `product` / `doc_ref` / `oper_pressure_*` columns; that was considered and rejected as re-typing what the finding already holds.
- **`perm_target_date` lives on `temp_repair`, not `findings.target_date`.** `target_date` is one of the five columns `pa_guard_repair_fields` blocks for inspectors, so writing it from this panel would break an inspector's save.
- **`src/workbench/temp-repair.ts`** (new, **strictly typed**, joins `assess-view.ts`/`repair-advisor.ts`) is the single presentation source: `tempRepairRows(tr, finding, assessInputs)` returns the bilingual `{section, label, value}` list for Excel sections 1–4, and **the detail page renders that array as `.d-item` pairs while `buildFindingPdf` renders the same array as autotable rows** — one list, so the screen and the printed record cannot disagree (same principle as `resolveIntegrityBanner` and `ganttBarGeom`). Also exports `tempRepairMethodKind`, `tempRepairMethodLabel`, `tempRepairHeadline`, `tempRepairResultColor`. Rows with an **empty label are continuation lines** (the anomaly narrative under 1.4, the test note under 3.4) — both renderers give them the full width instead of an empty label cell. Empty values are dropped entirely rather than printed as em-dashes, which is why the module wraps `paFmtDate`/`paFmtDateTime` (those return `'—'` for null).
- **Two levels of progressive disclosure**: `syncLeakAndAssessRules()` shows/hides the whole panel from `#fIsLeaking` (it already owns `#leakingBanner` and the assessment lockout, so one function keeps every leak-dependent piece in agreement), then `syncTempRepairFields()` shows the fields only when `#fTrInstalled` is ticked. The clamp-vs-composite field block is chosen via **`TEMP_REPAIR_METHOD_KIND[method]`, never the select's index** — reordering `TEMP_REPAIR_METHODS` must not swap one branch for the other. `collectTempRepair` writes only the selected branch's columns and nulls the other's, so switching method can't leave stale clamp data on a composite record.
- **Labels are bilingual (Thai first, English second)** so the generated report maps onto the legacy Excel an auditor already recognises; technical nouns stay English inside the Thai, the same split `repair-advisor.ts` uses.
- The two photo groups are `PHOTO_GRID_SETS` entries carrying `group` (the wrapper to hide wholesale) and `scope` (`'detail'` vs `'form'`) — **the two surfaces decide visibility from different places**: the detail page from `currentTempRepair`, the edit form from its own possibly-unsaved `#fTrInstalled` switch, because `current` can point at a different finding on the form (it is reachable without visiting a detail page). Either way an already-attached photo of that kind also counts, so deleting the last one can't hide the group and strand the rest.
- **ASME PCC-2 part citations were corrected app-wide** in the same change: Part 2 = Welded Repairs, Part 3 = Mechanical Repairs (bolted clamp), Part 4 = Nonmetallic/Bonded (composite, ISO 24817). `REPAIR_METHOD_OPTIONS` and four `repair-advisor.ts` strings had them reversed. Findings whose saved `repair_method` used an old string now fall into the status dialog's existing legacy path (pre-selects 'Other', prefills the free text) — nothing is lost, but they read as "Other" until normalised.

### Inspection Plan (`#/plan`, `#viewPlan`, `src/features/plan.ts`)

The scheduling module. A **plan** is a programme header scoped by year + terminal + pipe category (Underground / Sub Sea / Piping); under it sit free-text **tasks**, each with a PLANNED and an ACTUAL month range, drawn on a Gantt as two stacked bars (outline = commitment, solid = what happened).

- **Months are stored as real `date`s pinned to the 1st** (`'2026-03-01'`), not int month numbers — so a plan can span a year boundary, and the app's existing ISO-string date idiom (lexical compare, `fmtDate`, `todayISO`) applies unchanged. `<input type="month">` yields `YYYY-MM`; `monthInputToIso()`/`isoToMonthInput()` bridge it.
- **`plan_task.pipe_tag` is a soft reference with no FK**, preserving `line_list`'s invariant that re-importing it can never break saved data. It may name a tag that no longer exists.
- **`pipe_category` lives on the plan, not on `line_list`** — a manual per-plan attribute. Do not add a category column to `line_list`; that edges toward the pipe-asset register this app deliberately doesn't have.
- **The maintenance layer is derived, never stored.** Findings with a due date (`dueDateOf`) render as one-month markers coloured by `STATUS_COLORS`, outlined heavier when `isOverdue()`. Reusing those helpers verbatim means the timeline can't disagree with the register. **Repair work has no start date anywhere in the data, so none is invented** — a maintenance bar is one month wide, a due-by marker rather than a fake span. `maintenanceRows(startIdx, months)` filters to the visible range and the KPI tile counts that same set: without the range filter a finding due outside the year still produced a labelled row whose bar `ganttBarGeom` correctly refused to draw, leaving a visibly empty track.
- **RLS is blanket authenticated read+write** (unlike `line_list`'s read-all/write-maintenance) — inspection scheduling is inspector work; repair scheduling/cost/closeout stays maintenance-owned on `findings` via `pa_guard_repair_fields`. To tighten it, swap the two policies in `db/schema.sql` section 10.
- **`ganttBarGeom(startISO, endISO, rangeStartIdx, monthCount)` is pure and shared with the PDF.** The web multiplies its fractions by 100 into `%`; `buildPlanPdf` multiplies them by a millimetre track width. One source of truth — the same principle as `resolveIntegrityBanner` and re-deriving through `computeB313`. It lives in `plan.ts` and `pdf.ts` imports it (dynamically, at call time — both directions are `await import()`, so there's no module-eval cycle).
- The Gantt is **divs + inline percentages, no charting library and no SVG**, extending the `.stack-row`/`.mech-row` idiom. frappe-gantt (MIT, ~50KB, the only serious vanilla candidate) was evaluated and rejected: dual plan-vs-actual bars per row and derived read-only overlay rows are not Gantt primitives, and the PDF requirement is better served by drawing vectors directly.
- Year options come from plan years **plus every year a finding is due**, since the maintenance overlay exists before any plan does; the page opens on the *current* year when available rather than the newest.

### Line Risk Ranking (`#/risk`, `#viewRisk`, `src/features/risk.ts`)

A qualitative risk ranking of piping **lines** (not individual findings), rolled up from each line's findings' ASME B31.3 status — deliberately named "Risk Ranking," **not** "POF": there's no real API 581 quantitative POF here (no damage-factor tables, inspection-effectiveness history, or consequence modeling), and naming it POF would risk the numbers being mistaken for a certified RBI figure.

- **Line = `pipe_tag`.** A finding with no `pipe_tag` can't group into a line, so it becomes its own single-finding pseudo-line keyed by `location_desc` (mirrors the tag-fallback convention used everywhere else in the app). `location_desc` and `finding_type` (damage mechanism) both live on the *finding*, not the line — `line_list` has no location or mechanism column at all — so a multi-finding line can have multiple locations **and** multiple mechanisms; both are surfaced honestly (a location count + up to 2 mechanism chips, `mechChipsHtml`), never flattened to one value.
- **Risk band** = worst ASME B31.3 status across the line's assessed findings (REPAIR > MONITOR > OK), re-derived from each finding's *latest* assessment snapshot via `resFromSnapshot()` (`detail.ts` — same function the detail page uses, so the two pages can never disagree). Non-wall-loss finding types (Dent, Coating, Pipe Support Defect, Other) never get a `computeB313` result and sit permanently in a separate **Not Assessed** band — deliberately still shown rather than excluded, since a bad Dent is a real risk even without a numeric wall-thickness score.
- `loadRiskData()` bulk-loads every finding's assessment history in one query (not per-finding like the detail page) and keeps only the latest row per `finding_id` client-side into `riskAssessments` (`core/state.ts`). `computeLineRisk()` groups+rolls up; sort is band first, then ascending remaining life within a band (lines with no computed remaining life sort last), Not-Assessed always last.
- **Sticky toolbar** matches the Detail page's pattern exactly: `.toolbar-id-row` wraps the back-link + `.risk-toolbar-title` (static text, so — unlike `.detail-head h2` — it does **not** need the `'Noto Sans Thai'` fallback in its font stack) so the page identity and the Terminal filter / "Include repaired / closed" switch stay pinned while the KPI band, charts, and table scroll beneath.
- Two charts, both built from `computeLineRisk()`'s output, no charting library: `renderRiskTerminalChart` (stacked bar per terminal, band composition) and `renderRiskMechanismChart` (bar per damage mechanism, High-risk lines only) — the mechanism chart's bar colors come straight from `TYPE_COLORS`, so a `TYPE_COLORS` change (see `core/constants.ts` above) reflects here and on the dashboard map automatically, never a second palette to keep in sync.
- The ranked table's rows are collapsible: a multi-finding line renders one summary `<tr class="line-row" data-line-key="…">` followed by its (initially `display:none`) `child-row`s, toggled open/closed on click. The summary row's `.expand-caret` is **always** rendered in the markup (just `visibility:hidden` on single-finding rows) — omitting it entirely on single-finding rows left their tag text ~19px left of multi-finding rows', breaking column alignment down the table; keep this "reserve the slot, hide the content" pattern for any future column that's conditionally present per-row.

Don't reintroduce a signature grid.
- `PDF_NAVY_TINT`/`PDF_PANEL` are neutral-fill constants available for these blocks (kept even though the current layout inlines its tints).
- **Governing Equations use a two-level layout** (both `buildFindingPdf` and `buildQuickCalcPdf`, kept visually identical as one report family): each equation is the **symbolic formula** as a navy-bold heading (with the standard reference right-aligned via `FS_CAPTION` in the finding PDF / `FS_DISCLAIMER` in Quick Calc), then the **substituted computation** (the real stacked fraction from `drawFractionRow`) rendered in plain dark monospace, lightly indented (`M + 4`) beneath it. The navy-bold-sans-vs-dark-monospace contrast plus the small indent carry the "formula → worked numbers" hierarchy. This deliberately replaced an earlier flat layout where the bold formula label and the monospace substituted line both read as near-identical `var = expr` rows — a user couldn't tell the formula from the worked numbers. **A richer version was built then progressively stripped at the user's request** — it originally had a numbered navy step chip per equation, and the worked line sat on a light `#f8fafc` computation band with a navy left accent; the chip, band, and accent were all removed one by one, leaving the current minimal form. (When removing the band, `y += bandH + 3` was left dangling referencing the deleted `bandH` — a real runtime `ReferenceError` that build/typecheck didn't catch, only a live PDF export did; now `y += workedH + 3`.) The per-equation heights are tuned (`workedH` 11mm fraction / 6mm flat, +3mm gap) so all six equations + Scope + Status History still fit without spilling the `— End of Report —` marker onto an extra page — **re-verify the page count with a live render if you change these**, this exact overflow happened once (5→6 pages) and had to be tightened back.

Content order **= the shared form/detail order**: **title block** (banner + identity grid + QR) → **Location** (description, coordinates with a Google-Maps link, 140 mm satellite figure) → **Anomaly** (Defect L×W, Actively Leaking, Description — Type/Severity are in the grid) → **Photographic Record** (As Found → Before Temporary Repair → After Temporary Repair → After Repair) → **Temporary Repair Record** (only when a `temp_repair` row exists) → **Line Identification** (tag, P&ID, service) → **Reference & Planning** (source-report link, SAP notification/order, target/re-inspect/repair dates when set, closing note, recorded-at) → **ASME B31.3 Wall-Thickness Assessment** as ONE numbered section (band + verdict + provenance, then sub-parts N.1 Input Parameters, N.2 Cross-Section, N.3 Calculation Results, N.4 Governing Equations, N.5 Scope & Limitations) → **Repair Advisor** → Status History → closing. All label/value sections go through the local `kvTable(pairs)` (pairs with `full:true` span the row; an odd trailing pair spans instead of leaving empty cells; `emph`/`url` supported). The advisor's standards note and the temp-repair provenance note are each their **table's last row**, so they can't be orphaned onto the next page. When the wall is at/below CA the "with CA reserved" equations print `n/a — wall below CA` (shared `buildEquationRows`), not a fraction over "—". A legacy snapshot that can't re-compute falls back to a compact saved-results section.

**Repair Advisor section** (after the ASME B31.3 assessment section — the numbers, then what to do about them — the detail page's order; its callout title comes from the shared `advisorBanner()`): **always rendered, never gated on an assessment existing** (the earlier CLAUDE.md claimed this but the code never actually rendered it — `resolveAdvisor` was an unused import until it was wired in). Built from `resolveAdvisor(f.finding_type, assessRes, f.is_leaking)`, mirroring `paRenderRepairAdvisor`'s status/leaking precedence: a colored banner callout (same light-tint + colored-spine language as the integrity band — REPAIR/leaking red, MONITOR amber, OK green, else navy "ASME PCC-2 / API 570 GUIDANCE") + the Thai `summary`, then a title/body autotable of the resolved `items` (navy-bold label column like the metadata tables; each item's `sub[]` points become `•`-bulleted lines in the body cell), then the `standardsNote` + `needsReview` caveat as an italic footnote. Status- and mechanism-aware, leaking-overlay safety block prepended when `is_leaking`. Thai prose keeps English technical nouns (Composite, Welded, WPS/PQR, Pre-heat, NDT, Cathodic Protection, etc.) — same split as the web panel.

Numbers are **re-derived from saved inputs through `computeB313`**, so PDF and web UI can never disagree. All images are pre-awaited before drawing. Semantic colors are named constants (`PDF_OK`/`PDF_WARN`/`PDF_DANGER`/`PDF_NAVY`/etc.) — never re-type hex per call site. **Only WinAnsi-safe characters** in PDF strings (no `≥`/`≤` — use `>=`/`<=`). Export uses the `blob:`-anchor native-viewer approach — never `window.open`+`.location` or `data:` URLs.

**Font-size type scales**: every `setFontSize()` call across all **five** PDF builders (`buildFindingPdf`, `buildQuickCalcPdf`, `buildSummaryPdf`, `buildSlidesPdf`, `buildPlanPdf`) goes through named `FS_*` names — **no bare numeric literal appears anywhere in any of them**. **The four document PDFs now take theirs from the shared `DOC_FS`** (see "One PDF family" above); only `buildSlidesPdf` keeps its own local projected-screen scale. (History: each function used to have its own locally-scoped scale, following the same naming pattern (`FS_MICRO`/`FS_LABEL`/`FS_BODY`/`FS_VALUE`/`FS_TITLE`/`FS_HERO` etc., with a couple of function-specific extras like `FS_CAPTION`/`FS_DISCLAIMER`/`FS_SUMMARY` where a genuinely distinct role exists). This consolidated ~44 near-duplicate ad hoc sizes total (11 in `buildFindingPdf`, 8 in `buildQuickCalcPdf`, 7 in `buildSummaryPdf`, ~18 in `buildSlidesPdf` before its own earlier pass) down to under a dozen named roles per function — accumulated over many rounds of "make it bigger"/"make it smaller" edits with no scale discipline.) **One exception is deliberate, not an oversight**: `buildFindingPdf`'s `tbCell` identity-grid helper (the top-of-report Line Tag/Terminal/Finding Type/Severity/Report Ref/Status/Inspection Date/Recorded By grid) keeps a per-call `opts.fs` literal override (8.5/8/9.5/9/7.5) — these are tuned per grid cell to fit that specific cell's content width (e.g. short "Severity" gets a larger size, longer "Finding Type" gets a smaller one so it doesn't wrap awkwardly), not meaningless near-duplicates, so don't try to collapse them into one shared constant. When adding a new label/value anywhere in any of the four builders, reuse an existing constant for that role rather than typing a new number — a fresh literal is exactly how the sprawl reappears.

## Running / testing

- `npm run dev` for local development; full function needs a network connection (Supabase).
- **Automated suite is just the one Vitest file** (`compute.test.ts`, the parity gate). Everything else is verified with **ad hoc Playwright scripts written to the session scratchpad** — not checked into the repo, recreated per verification pass. Pattern established across many sessions: sign in with real credentials (never hardcoded/committed — supply via env vars or ask the user), exercise the feature in-browser, assert on rendered DOM/PDF content, then clean up any test finding created (clearly tagged, e.g. `TEST-E2E-...`, deleted at the end of the script).
- Headless Chromium does not paint iframe PDF viewers — verify generated PDF *content* by exporting the blob bytes and reading them with `pdfjs-dist` (`legacy/build/pdf.js` build works outside a browser) rather than a DOM screenshot.
- For anything touching saved data or PDF output specifically, run the authenticated E2E pass described in the extraction-pattern note above before calling a change verified — build/typecheck alone has repeatedly missed real runtime bugs (the Thai `splitTextToSize` bug, an unused-import miss, etc.).

## Conventions to preserve

- Pressure entered in `bar`/`psi`, always converted to **MPa** internally (inside `computeB313`).
- The app has no dark mode — a single light palette only. The app header (`body > header`) is sticky with a thin teal→sky `.header-accent-bar` and the OR logo in a `.hdr-logo-chip`. `syncHeaderHeight()` measures it into `--app-header-h` for anything else sticky. The logo `<img>` carries explicit `width`/`height` attributes to avoid a FOUC/CLS flash on first paint (the browser reserves the box before CSS/the image itself loads).
- **Navigation is the Menu drop-down; toolbars still wrap, never hamburger.** Primary navigation is the **Menu drop-down** (`#topNav` — see the Main menu section above; anchored under its button, never a centred dialog). Every *other* row (`body > header .wrap`, `.panel-h`/`.panel-h-btns`, `.map-toolbar`, `.filters`, `.form-actions`) still degrades by **wrapping onto additional rows**, never by collapsing into a menu — keep new toolbars consistent with that. **Two real regressions have shipped from getting page width wrong, both the same failure mode — content dragged wider than the physical screen:**
  1. `body > header .wrap` once had a `@media (max-width: 480px) { flex-wrap: nowrap }` override tuned for a 2-3 button header. When the roles feature grew it to 5-6 items, nothing clipped the overflow and `document.documentElement.scrollWidth` exceeded the viewport on *every* authenticated page, not just the header. Fixed by wrapping. (This is the reason nav moved to a sidebar — the top row now stays short permanently.)
  2. The sidebar migration itself reintroduced it: `main.wrap`'s base rule sets `width: 100%`, which resolves against the **viewport**, so adding `margin-left: var(--sidebar-w)` put the page 240px wider than the screen (measured `scrollWidth` 1625 vs `innerWidth` 1400). Fixed with `width: auto` in the offset rule so the block fills only what's left after the margin.
  **Lesson: any rule that indents or constrains the page container must be checked with `document.documentElement.scrollWidth <= window.innerWidth` on every view, at both desktop and phone widths.** That assertion is in the E2E script and is cheap to re-run. `.form-section-nav`'s pill-tab strip relies on `overflow-x: auto` instead of wrapping (by design — a scrollable strip, not a reflowing row) with an `::after` edge-fade so a cut-off last tab reads as swipeable.
- Two reading modes (wall-loss depth, listed first / measured thickness) tracked via `.active` on the mode segment buttons; mutually derivable (`t_meas = t_nom − depth`).
- Validation uses `aria-invalid="true"` + `.validation-alert` visibility.
- All numeric display formatting goes through `paFmt(val, decimals)` (`—` for null/non-finite); `fmtN` is the PDF-local equivalent.
- **One font: Google Sans everywhere** (web + PDF) for Latin/numeric text, **Noto Sans Thai** for Thai text (see above) — "Google Sans" is proprietary and not on the public Google Fonts API, so `registerGoogleSansWebFont()` injects an `@font-face` from the same embedded base64 TTFs the PDF uses. Only Regular(400)+Bold(700) exist, mapped via weight ranges. No JetBrains Mono / no Google Fonts CDN link — numerics keep `font-variant-numeric: tabular-nums` so figures still column-align. Dense-engineering styling: hairline borders, `--radius: 0.5rem`, spacing tuned per component in small (~2–4px) increments; border-radius scale **6px** interactive controls / **8px** containers, pills use `height/2`.
- **Form fields fill their grid cell, and `.fgrid` columns are equal** (`repeat(2, minmax(0, 1fr))` + `.fgrid .select { width: 100% }`). Basecoat sizes `.select` to `fit-content` and a plain `1fr` track cannot shrink below its content, so selects used to land at random widths (80px NPS beside a 310px Material) and one long option widened a whole column. Only the pressure-unit select in `.p-row` stays compact.
- **Two page widths only**: the single-record pages (finding detail `.detail-flow` + `#detailHealthBanner`, finding form `.form-flow`, Quick Calc `.quick-calc-wrap`) are capped at one token, `--page-read-w` (1280px, theme.css) — Quick Calc was 1200 and visibly narrower than the others; the data pages (dashboard, risk, plan, line list, users) use the full `.wrap` width for their maps/tables/Gantt. A new single-record page uses the token, never its own number.
- **Space use** (from a signed-in audit): page width `.wrap` max 1760px (was 1500px — a 1920px screen had ~210px of empty margin each side). Register rows: 72px thumbnail, and on ≥1100px the tag cell is a 2-column grid — identity (`.t-ident`: tag + type) | details (`.t-detail`: Loc / Anomaly lines) — so a row is two lines instead of four; on ≥641px the table is `table-layout: fixed` with fixed Status / Terminal / Age / Due widths so those columns sit beside the content instead of at the far edge. Result: ~10 findings per 1080p screen instead of 3. Detail page: the right column becomes `position: sticky` (`.detail-col.is-sticky`, set by `syncDetailSticky()` in detail.ts with a ResizeObserver) **only when it is shorter than the left column AND fits the viewport** — a sticky column taller than the screen would hide its own lower part. Finding PDF: photos are **three per row** (short "Figure N: photo k" captions — the group heading names the group) and the photo section reserves one 3-up row, so page 1 no longer leaves ~80mm blank before the photos.
- **Spacing & control sizes (web UI)** — every `padding`/`margin`/`gap` in `theme.css`/`app.css` uses a `--sp-N` token (`--sp-2 4 6 8 10 12 14 16 20 24 32`, named by px; the app's real grid is 2px steps, so that is the scale). Only `0`/`1px` hairlines and two component-internal values (the map select's 22px arrow room, the timeline's 22px dot indent) stay literal. Odd values (3/5/7/9/11/19) were snapped to the nearest step — don't reintroduce them; pick a step instead of typing a new number. **Two control heights only**: `--ctl-h` 36px (form fields, page-level buttons, filter/search boxes — a toolbar row must be uniform, so the Risk/Plan search boxes are 36 like the selects beside them) and `--ctl-h-sm` 28px (`.btn-sm`/`.select-sm`/`.input-sm`, the map toolbar, and **every control inside a `.panel-h`**). **Every `.panel-h` is 40px** (`--panel-h-min`; 6px padding + 28px controls), whether or not it carries a button — the dashboard register trims its header padding to compensate for its framed button group; only a header that wraps onto two rows on a phone is taller. `.sticky-page-header` is `8px 20px` (balanced; the inner `.toolbar` has no padding/margin of its own) and on phones also drops the finding header's meta line, compacts its buttons to 28px and tightens its gaps, so the pinned toolbar is ~70–110px instead of 94–154px. The detail **Details grid is 2 columns on phones** (`.dgrid` ≤640px); `dItem(label, html, true)` marks long values (location, coordinates, e-mail, report link) `.d-wide` to span both. `body.public-view` also hides `.photo-remove` and the temporary-repair photo groups' "+ Add" buttons (`#btnAddTempBefore/After` were missing from the hide list) (the read-only share used to show delete buttons). Verify spacing work with a before/after dump of computed paddings/margins/gaps/heights per view rather than by eye.
- Readability floor: **12px** (`--fs-sm`) for anything actively read; 11px (`--fs-xs`) only for short uppercase labels/eyebrows; 10px (`--fs-2xs`) only for badge chips / single glyphs. **Body text is 14px (`--fs-base`)** — the scale was raised one step across the board (it had 81% of on-screen text at 12px or below, with 12px body and 11px captions); measure with a computed-font-size histogram per view before/after any type change rather than eyeballing.
- **Font-size scale, web UI**: every `font-size:` declaration in `theme.css`/`app.css` resolves to one of 13 `--fs-*` custom properties defined in `theme.css`'s `:root` (`--fs-2xs` 10px through `--fs-display` 40px — current values: 2xs 10, xs 11, sm 12, base 14, md 15, lg 16, xl 17, 2xl 18, 3xl 20, 4xl 22, 5xl 24, hero 30, display 40 — `display` is for projected screens only, the Quick Calc presentation mode) — **no bare px value appears anywhere in either stylesheet** except one deliberately-relative `0.8em` (a `.panel-h h2::after` suffix meant to scale with whatever heading it's attached to, not pinned absolutely). This consolidated 19 raw px values (165 declarations, accumulated over many rounds of ad hoc sizing with no token backing — colors already had `--text-color`/`--text-muted`/`--text-light` tokens, font-size didn't) down to 12 named roles. `--fs-2xs` (10px) sits below the 12px readability floor and is scoped **only** to short uppercase badge/eyebrow chips or single glyphs (kbd hints, compact status pills, close-icon glyphs) — never body prose, consistent with the floor's own stated exception for short badge text. The KPI/heading cluster (`--fs-xl` 17px / `--fs-2xl` 18px / `--fs-3xl` 20px / `--fs-4xl` 22px / `--fs-5xl` 24px / `--fs-hero` 30px) is kept as six separate steps **on purpose, not merged** — several sit side by side in the same card (e.g. the KPI ring's percentage next to its smaller fraction), forming a real, deliberate visual hierarchy that collapsing would visibly flatten. When adding a new rule anywhere in either stylesheet, reuse an existing `--fs-*` token for that role rather than typing a raw number — a fresh literal is exactly how the sprawl reappears (same lesson learned consolidating the PDF builders' `setFontSize()` calls, see `features/pdf.ts` below).
- Semantic status colors (`--ok-color`/`--warn-color`/`--danger-color`) and cross-section limit colors (`--limit-*`) are CSS variables — never hardcode their hex in CSS/SVG attributes. The `--limit-*` values are dark 700–800-tier shades so 11px bold SVG labels clear WCAG AA against `--svg-bg`; the PDF renders via `paSvgToPng`'s injected style block, which duplicates this hex list as static values (CSS vars don't resolve in a standalone serialized SVG) — keep it in sync. `STATUS_COLORS`/`TYPE_COLORS`/`SEVERITY_COLORS` (`core/constants.ts`) are likewise fixed hex, deliberately theme-independent (drawn over satellite imagery, whose background never changes with app theme).
- **Toasts never block taps**: the toaster sits at the top, over the page toolbar, and Basecoat pauses a toast while the pointer is on it — on a phone a tap meant for Export PDF / Edit details hit the toast and kept it there. `.toaster .toast:not(:has(button)) { pointer-events: none }` lets taps through plain messages; toasts with an action button (the PWA "Reload") still take taps. One action = one toast: `saveForm` folds the "assessment pending" note into its single save message (it used to add a second, red one — saving location + damage + depth with no pipe data is the intended operator flow, not an error).
- **Touch devices (mobile-native audit, Oct 2026)** — `theme.css` ends with a touch baseline: no grey tap flash (`-webkit-tap-highlight-color: transparent`, with `:active { opacity: .8 }` press feedback instead), no landscape font inflation, `touch-action: manipulation` on controls (no double-tap wait), no long-press text selection on buttons/tabs, **every input/select/textarea is 16px (`--fs-lg`) under `(pointer: coarse)`** — iOS Safari zooms into any field under 16px and does not zoom back (25 selects/search boxes were 14px; `!important` because components set their own size — never fix it with `maximum-scale`), and **pull-to-refresh is off only while the finding form is open** (`html:has(#viewForm.active) { overscroll-behavior-y: none }` — an Android pull reloads the page and loses a half-typed finding). **Every `:hover` rule lives inside `@media (hover: hover) and (pointer: fine)`** (a tap fakes :hover and leaves it stuck) — mixed selector lists are split so `:focus-visible` stays ungated; write new hover rules the same way. Full-screen views use `100dvh` after a `100vh` fallback line (presentation overlay, sticky map panel, lightbox). Safe-area `env()` paddings exist on the FAB and the phone save bar but the viewport has no `viewport-fit=cover`, so they are 0 — only needed if the app goes edge-to-edge.
- **Field limits and plausible values (break-ui audit, Oct 2026)** — `FIELD_LIMITS` (`core/constants.ts`: Line No. 80, location 200, description 4000, P&ID 80, service 120) is the one table for the form's `maxlength`, the Excel import check and `db/limits-migration.sql` (char_length CHECKs + `estimated_cost >= 0`, mirrored in schema.sql §1 — **must be applied in Supabase**; existing data was checked to fit). `inspectionDateIssue(iso)` (`core/dom.ts`) → `'future'` (blocked in the form via `#errInspDate` + `max=today`, rejected on import) / `'old'` before 2000 (form asks `confirm()`, import rejects); the register's age shows "—" for either instead of "20751d"/"0d". The form also blocks a negative repair cost (`#errEstCost`). A date rule cannot be a DB CHECK (it would reference today).
- **Register on phones / paging** — the tag line (`.t-tag-row`) wraps so badges and the "Needs engineer" flag drop below the name; on ≤640px the Line No. wraps to 2 lines (line-clamp) and the flag is icon-only (ruler); ≤360px drops the row photo. Status pills show a short label on phones (`regPill`, `STATUS_SHORT`: Monitor / Planned …) in a 64px column (desktop column 150px fits "REPAIR PLANNED"). The register draws `REG_PAGE` (50) rows with **"Show 50 more" in `#regMore`, OUTSIDE the table** — as a `colspan` row it spanned the phone layout's hidden Terminal column and, under `table-layout: fixed`, stole ~80px from Line No.; `renderList` resets the page; `flashRow` (pin click) expands it to reach the row. Money over a billion reads "฿13.3B" (`paFmtBahtShort`); the head sub-line uses `Intl.ListFormat` ("BRP, KBY, and SRC"). The trend card is HTML bars (`.trend`), not a scaling SVG, so its text keeps 11px on a 320px phone.
- **Project skills** — `.claude/skills/break-ui` and `.claude/skills/mobile-native` (Emil Kowalski, MIT; read before installing — plain guidance). `src/dev/dashboard-fixtures.ts` is break-ui's worst-case / empty / one / 1,200-row data, used only in `npm run dev` via `?data=…` (toggle bottom-centre, shown only while a dataset is open); the production build drops it.
- The universal `* { transition: … }` rule in `theme.css` is the single source for state-change fades; components only declare their own `transition` for properties it doesn't cover.
- CSS cascade-order trap: an override placed *earlier* in the stylesheet than the base rule it targets, at equal specificity, silently loses (source order wins) — scope overrides tighter instead of relying on media-query placement alone.
- SVG/XML comments must never contain `--` (breaks `XMLSerializer` for the PDF export path), and JS block comments must never contain `*/` mid-text.
- **Content that should get domain-expert review**: `workbench/repair-advisor.ts`'s non-wall-loss guidance entries and `LEAKING_OVERLAY` are flagged `needsReview: true` in code — they're defensible drafts grounded in real standards (SSPC/NACE, API 570/579-1/583, PCC-2 Parts 3/4/6) but not verified by a domain engineer. Treat as shippable general guidance, not as settled/authoritative content to build further automation on top of without a review pass.
